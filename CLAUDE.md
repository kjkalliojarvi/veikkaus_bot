# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Builds a past-performance dataset of Finnish harness racing (ravit) from **two** sources — the Veikkaus open REST API (`https://www.veikkaus.fi/api/toto-info/v1`) for entries and the betting market, and Suomen Hippos's Heppa registry (`https://heppa.hippos.fi/heppa2_backend`) for the official results — crawling both into one raw JSON archive and parsing that into DuckDB. Requires Python >= 3.14, managed with `uv`.

`totodatacollectionstrategy.md` is the spec. Read §2b (the Phase 0 findings) before changing anything that touches the API — it records where the live API contradicts the rest of that plan.

## Commands

```bash
uv sync                                    # install deps into .venv (make install)
uv run veikkaus backfill --from 2021-01-01 # crawl the race calendar into data/raw/ (resumable)
uv run veikkaus heppa --from 2021-01-01    # crawl the Heppa meetings into data/raw/ (resumable)
uv run veikkaus heppa-horses               # crawl one registry record per horse (after heppa + parse)
uv run veikkaus heppa-foreign              # crawl the meetings abroad, for starts Finnish horses made there
                                           #   (add ones prev_start cannot name to foreign_meetings.csv)
uv run veikkaus heppa-stats                # crawl the registry's career totals: how much of each career is missing
uv run veikkaus parse                      # raw archive -> archive.* tables
uv run veikkaus status                     # crawl manifest progress, both sources
uv run veikkaus crosscheck                 # do the two sources agree? (strategy §8)
uv run veikkaus stats [name]               # TUI: one horse's, trainer's or driver's Heppa starts, nine ways, click a row for the starts (`horse` is an alias; `t` cycles subject)
uv run pytest tests                        # run tests (make run-tests)
uv build                                   # build sdist + wheel (make dist)
```

The CLI entry point is `veikkaus` (defined in `[project.scripts]` → `veikkaus_bot.__main__:veikkaus`).

## Architecture

One pipeline, in two halves that never run together: **fetching and parsing are deliberately separate**, so a parsing bug never costs a re-crawl and the raw responses survive even if the API is retired in the 2027 licensing transition (§4, §10 of the strategy).

- `models.py` — Pydantic models for both APIs: `Card` → `Race` → `Runner` plus `Stat` for Veikkaus, and `HeppaEvent` / `HeppaRaceEntry` → `HeppaRace` / `HeppaStart`, `HeppaHorse`, and `HeppaHorseStats` → `HeppaHorseStatLine` for Heppa. Validation only; nothing here fetches. `HeppaStart` serves both the Finnish meetings and the ones abroad — same endpoint, same payload — and its `finnishTrack` is what tells them apart.
- `fetcher.py` — `Fetcher` does one request at a time: base delay 2 s ±30 % jitter, retries 429/5xx/timeouts through 30 s → 2 min → 10 min, and raises `CircuitOpen` after 5 consecutive failures. 400/404 mean "nothing there", not an error. `base_url` selects the host, so one instance serves one API and the two sources never spend each other's politeness budget. `store_raw()`/`read_raw()` are the gzipped raw zone, laid out as `data/raw/{meetDate}/card_{cardId}/…`. `VEIKKAUS_CONTACT` sets the contact address in the `User-Agent`.
- `crawler.py` — `Manifest` is the fetch ledger (`archive.manifest`, PK `(endpointType, entityId)`); `enqueue` uses `INSERT OR IGNORE` so re-running a window never re-fetches finished work. `next_pending()` orders by `meetDate DESC, stage ASC` — newest season first (§6), cards before races before per-race payloads — and filters on a tuple of endpoint types, `VEIKKAUS_TYPES` or `HEPPA_TYPES`, so a run of one source never fetches the other's rows. `crawl()` takes the crawl graph as an `expander` callable and knows nothing about either API; `expand()` is the Veikkaus graph. Kill and rerun to resume.

  **The multi-leg pools are a second Veikkaus opt-in, `LEG_TYPES`, and the whole point of it is that they are backfillable.** `/pool/{poolId}/odds` returns one row per *(leg, runner)* for a T-pool where it returns one per runner for the win pool — `legNumber`, `raceId`, `runnerNumber`, `percentage` (hundredths of a percent, ~10000 per leg), `amount`, `winProbable` — and those are the T-pool betting percentages, which exist nowhere else in the API. A runners payload's `betPercentages` has **only** the single-race pools: KAK 32,277, TRO 7,697, DUO 6,074, EKS 98 over a 3,000-payload sample of the raw zone and not one T-pool row, in any era. So `archive.bet_percentage` never held them and never could.

  Unlike every other Veikkaus figure, these **do not have to be captured live**. `stats` and `prevStarts` ride along only while a card is current, and the win odds are a pre-post-time snapshot, but a T-pool's odds payload keeps its closing percentages indefinitely — verified against the archive's first day, where `/pool/7739521/odds` still returns all 81 rows of the Toto75 of 2021-01-02, `netSales` 35,240,376, frozen at its final `updated`. Field-for-field the 2021 and 2026 payloads agree; only `scratched` (2026, absent in 2021) and `t4percent` (2021, meaning unclear, not stored) differ.

  `expand()` follows a pools payload into **both** kinds of child, `odds` for `VOI` and `leg_odds` for `LEG_POOL_TYPES`, and `_pool_odds_task()` is one definition of the URL and raw path for the two — same endpoint, different endpoint type, so each can be crawled, limited and re-fetched on its own. Pool ids are unique across types, so they cannot collide on the manifest or in the raw zone. A multi-leg pool is listed by *every one of its legs*, so it is enqueued once per leg race; all legs sit on one card (verified: 0 of 3,182 pools span two cards or two dates), so the duplicates agree on date and card and `INSERT OR IGNORE` keeps the first.

  **`LEG_POOL_TYPES` is an explicit tuple rather than a rule, and `hasCombinations` is why it looks like it should not be.** That field is present on every T-pool row of every archived pools payload and absent from every VOI/SIJ/KAK/DUO/TRO/EKS one — 14,261 against 0, so as a *selector* it is exact — but it arrives `false` on 1,384 of them, which makes it a live-state flag (are the combinations published yet) and not an identity. Predicating identity on a state flag breaks quietly, so the tuple decides and the field is used only to *report*: `_leg_pool_tasks()` counts pool types carrying it that the tuple does not name and `leg-percentages` prints them, which turns a new Veikkaus product into a printed line rather than data silently missing. Same reflex as `EMPTY_MEETINGS` in the foreign crawl. T86 is in the tuple and has never been observed.

  **`_leg_pool_tasks()` is driven by the raw zone, not by the parsed archive** — the only archive-driven crawl in the repo that is. The pool ids exist nowhere but inside the `pools` payloads, and `archive.odds_snapshot` holds VOI ids only, so it reads the 26,348 archived payloads back off disk (~13 s) instead of re-requesting a pools listing per card (~1.5 h). That also means `leg-percentages` needs a `backfill --odds` in front of it and **not** a `parse`, unlike `heppa-horses`/`heppa-foreign`/`heppa-stats`.
- `heppa.py` — the Heppa crawl graph, same shape as `crawler.py`. Seven endpoint types: `heppa_results` (one date range → the meetings), `heppa_races` (one meeting → its races), `heppa_start` (one race → the whole field), `heppa_horse` (one horse's registry record), `heppa_foreign_races` and `heppa_foreign_start` (a meeting abroad and its field), and `heppa_horse_stat` (the registry's own career totals). Stages 10-16, above the Veikkaus 0-5. Reuses `Manifest`, `Fetcher` and `crawl()` whole. **Four separate opt-ins, each with its own type tuple** — `HEPPA_TYPES`, `HEPPA_HORSE_TYPES`, `HEPPA_FOREIGN_TYPES`, `HEPPA_STAT_TYPES` — so a one-day results run cannot kick off an eight-hour horse crawl, and so a foreign run cannot drain the meetings crawl's pending rows. The last three are driven by the *archive* rather than by a date window, so each has to follow a `heppa` crawl and a `parse`.

  **The starts abroad, and why they need a second discovery pass.** Heppa records a Finnish-registered horse's foreign starts and serves them through the *same* per-meeting endpoints as the home ones — `/race/2026-05-30/SV/races` returns 8 races and `/race/2026-05-30/SV/start/3` returns the two Finnish runners, Combat Fighter 4th included, with placing, km time, driver, trainer and prize. It just never *lists* those meetings: `finnishTrack` on a results-listing event has never once been false (0 of the 301 events of 2026), so the crawl had no way to learn they exist. `FOREIGN_MEETINGS` reads the (date, track) pairs out of `archive.prev_start` instead — Veikkaus ships a horse's own career line, foreign starts included — which found 356 meetings at 44 tracks, 2023-09 to 2026-08.

  **That query excludes on `archive.heppa_event`, not on `archive.heppa_start`, and the difference is a self-poisoning bug.** heppa_event comes from the Finnish-only listing, so it can never name a track abroad. heppa_start can, the moment this crawl succeeds once — and then the next run would exclude exactly the tracks it had just learnt about and discover nothing, which looks like a crawl that finished rather than one that found nothing. The `Hr2` → `HR` fold is applied before the comparison for the same class of reason: without it Härmä reads as foreign and the crawl re-fetches 28 Finnish meetings it already has.

  **A foreign row is thinner in two places, and neither is a parse fault.** `startTrack` comes back 0 where the foreign programme's post is not recorded (Vincennes), against 1-15 at every Finnish meeting; and `kmTime` is the empty string wherever there is no time, with `kmTimeMs` correctly NULL beside it — though that second one is *not* new here, 53,767 of the archive's Finnish rows already store `''`, so `WHERE kmTime IS NULL` has always found none of them.

  **Discovery is at *meeting* grain, and that is why it recovers far more than `prev_start` holds.** One `prev_start` row unlocks the whole meeting: the crawl fetches every race with a Finnish runner and every Finnish-registered horse in it. Measured over the full crawl — 364 meetings, 44 tracks, 1,579 start payloads — it loaded **3,216 starts over 1,048 horses, of which `prev_start` held only 660: 2,556, four fifths, were new.** 752 canonical horses gained starts; 2,656 of the 3,216 rows resolved to a `horseKey`. Busiest by far is Bollnäs (BO), 45 meetings and 1,507 starts, then Solvalla (SV) 34/348 and Solvalla-Farsta (SF) 18/203.

  **`foreign_meetings.csv` is where knowledge from outside the archive goes** (`SEED_FILE`, `--seeds`, `read_seeds()`): one `date,trackCode` per line, `#` for comments, unioned with the query. It exists because guessing is cheap and the archive's blind spots are not guessable — a meeting that never happened, a track that never held one, and a real track on a quiet day all answer `200` with `[]` in **two bytes**, so a wrong seed costs one request. The flip side is that those three are *indistinguishable*, which is why `backfill_foreign` reports which seeded meetings listed no races (`EMPTY_MEETINGS`, read from the manifest: a races task with no `heppa_foreign_start` child is an empty listing) rather than letting a mistyped code pass for a quiet day. A seeded *Finnish* track is skipped and named — `heppa` already covers it, and fetching it again under the foreign types would store the same rows against a second raw path. And because an empty listing is recorded `done` rather than `failed`, `--retry-failed` cannot reset a seed whose results were not published yet; `--refetch-from` is what does, which is why `backfill_foreign` calls `refetch_window` as `backfill` and `heppa` do.

  **Backfilling further back does not improve discovery, and assuming it does is the easy mistake.** `prevStarts` rides along in a runners payload only while the card is current, so `prev_start` reflects *when* you crawled and not *what range*: 643 Veikkaus cards were crawled for 2021 and yielded **4** `prev_start` rows and **zero** foreign ones, against 12,861 and 408 for 2026. So discovery grows *forward* — each cycle over recent dates enriches `prev_start`, and re-running `heppa-foreign` costs only the newly-visible meetings. For anything before about 2024 the seed file is the only route: of the nine foreign meetings the archive holds before 2024, **six are seeded and three were found**.

  **It is partial by construction, and `heppa-stats` is how you know by how much.** A meeting is discoverable only if Veikkaus re-reported one of its horses, or somebody put it in the seed file. Measured on Combat Fighter: `/horse/{id}/stats` says 81 career starts and 16 for 2026; the archive held 27 and 9, and the foreign crawl took 2026 to 10. Its 2023 and early-2024 Swedish starts predate its Finnish registration and are unreachable from here at all. Heppa also returns only the Finnish-registered runners of a race abroad, so a foreign row's field is our horses and not the whole race.

  **What is *not* a crawl target: the legacy Tapestry app.** `/heppa/app?page=horse/RacingHistory` does hold a horse's whole start list, but its form posts to `/heppa/horse/RacingHistory,$HorseSearchArea.form.direct`, and robots.txt disallows `/heppa/horse`. `heppa2_backend` stays the only surface used, which is the one robots.txt does not name. There is also no per-horse start endpoint there: `/horse/{id}/starts` returns 400 *"Invalid resource name"* (as do `/driver/…` and `/trainer/…`, while a nonsense subresource returns a plain 404 — the `/…/starts` route takes only `race`, which wants a date), and `results`, `racing`, `races`, `racedays`, `history`, `racingHistory` and the Finnish spellings all 404.
- `archive_db.py` — the `archive` schema, its upserts, and the shared DuckDB helpers (`db_ops`, `db_read`, `_insert_many`). Tables: `card`, `race`, `horse`, `start`, `prev_start`, `stat`, `bet_percentage`, `odds_snapshot`, `leg_percentage`, `heppa_event`, `heppa_race`, `heppa_start`, `heppa_horse`, `heppa_horse_stat`, `manifest`.
- `parse.py` — walks the manifest's `done` rows, reads the raw files, upserts. Idempotent. Holds the Finnish km-time parser, `horse_key()`, and the Heppa scalar parsers. `_parse_heppa_starts` consumes **two** endpoint types, `heppa_start` and `heppa_foreign_start`, in one loop: the same payload from the same endpoint into the same table, differing only in how the meeting was discovered. It **drops a start with no `horseId`** and says so — that column joined the primary key when the starts abroad arrived, DuckDB will not hold a NULL there, and one such row would fail the whole batch it rides in rather than itself. `_store_leg_percentages` drops a leg row with no `legNumber` or `runnerNumber` for exactly that reason, and needs no sibling payload the way `_store_odds` needs the pools listing: a leg row names its own race, and `netSales`/`netPool`/`updated` are on the payload.
- `crosscheck.py` — read-only validation of the two sources against each other (strategy §8). Builds every report on `archive_db.HEPPA_START_BRIDGE`, the same join the merge uses, so the check cannot drift from what it is checking. **Its unmatched-meeting report filters `finnishTrack`** and the starts abroad get one of their own, `Starts abroad: what the foreign crawl reached` — a meeting abroad has no Veikkaus card *by design*, so 364 of them in the unmatched report would drown the vocabulary gap it exists to catch (it stayed at 218 PAIKALLISRAVI / 83 PONI / 2 TOTO after the full crawl). That report's `horse_resolved` is legitimately short of every row: the horseId→horseKey mapping is built from races both sources cover, so a horse whose Finnish starts fall outside the Veikkaus crawl has no `archive.horse` row to resolve to.
- `horse_stats.py` — the SQL behind `veikkaus stats`: a search and nine breakdowns of `archive.heppa_start` (overall, shoe combination, cart, distance class, start type, post position, `startInterval` bucket, track, and the counterpart role), each counting starts, 1st/2nd/3rd, disqualifications and gallops, **for any of three subjects — a horse, a trainer or a driver**. **The gallop column overlaps the placings rather than competing with them** — a horse can gallop and still win, and 48,078 of the archive's 51,730 galloping starts were placed at all, 2,832 of them first — so it reads as 'how often did it break under these conditions', never as a fourth outcome. **`dq` is the opposite, and that is why it sits on the other side of the spacer column**: `disqualifiedCode` is non-NULL on 36,513 of the 298,492 non-absent rows (hpl 16,696, hll 11,174, k 4,007, hlo 3,543 and six rarer codes) and **not one of them carries a placement**, so a disqualification competes with 1st/2nd/3rd and is counted beside them, while `gallop` stays alone behind the gap (3,765 rows are both). `PLACINGS` therefore orders `starts, 1st, 2nd, 3rd, dq, gallop`, which is **deliberately the reverse of sjoden**, where `dq` is appended last and `_spaced()` gaps the final two — copying that here would say the opposite of what is true, and it is why `horse_tui._spaced()` did not change. **Distance class strips the `a` prefix** — Heppa's eight `distanceCode` values are four classes and a start-type marker (`ke`/`ake`, `ly`/`aly`, `kp`/`akp`, `pi`/`api`), and the marker is the start-type breakdown's own axis, so keeping it would split every class in two and ask one question twice. Both tables order short-to-long or by starts, never by label: alphabetically the classes come out ke, kp, ly, pi. **The two are the same fact read twice on a Heppa row** — `parse_heppa_auto_start()` derives `autoStart` from that prefix, verified 1:1 over the archive (110,496 `ake` rows, 110,496 auto) — so the start-type table always mirrors the a/bare split; it reads the parsed column rather than re-deriving it because that column is what analysis joins on. Every function takes an open connection, so the SQL is testable the way the rest of the suite tests SQL, and `COMMON` is a tuple of `Axis` records in `crosscheck.REPORTS`'s shape — a tenth breakdown is one entry, with no UI code and no drill-down code. `breakdowns(subject)` appends that subject's counterpart-role axis, and `AXIS_COUNT` is **constant across subjects**, which is the property the widget code depends on. `Axis` is defined above `Subject` because `Subject.partner` is annotated `Axis` and a NamedTuple evaluates its annotations when the class body runs; the two `Axis` methods take `'Subject'` as a forward reference for the mirror image of the same reason.

  **Whose starts are counted is a `Subject`, and it is the only thing that varies** — the FROM/WHERE, the drill-down's SELECT list, the search query, **and which counterpart role its last axis asks about**. `PLACINGS`, every label expression, their sort keys and the absent filter are shared verbatim, which is the whole reason there is no `trainer_stats.py` and no `driver_stats.py`: a second copy would be a second definition of what `'<= 14 days'` means, exactly the drift `crosscheck` avoids by building on `HEPPA_START_BRIDGE`. **`partner` is what makes the third subject cost one line rather than a widget rewrite** — a horse and a trainer get `DRIVER_AXIS`, a driver gets `TRAINER_AXIS`, because asking a driver which drivers drove it returns one row equal to Overall. Every subject answers `AXIS_COUNT` axes, so the UI retitles a panel rather than rebuilding a tree. The `frm` fragment is a three-part contract — the table is aliased `hs` (every shared expression says `hs.`), it takes exactly one `?` (the identity, so `bucket_starts` builds its parameters without knowing the subject), and it *ends* in a `WHERE` so `Axis.starts` can hang `AND <label> = ?` off it. `Axis.breakdown`/`Axis.starts` are therefore methods taking the subject, not properties.

  **A trainer is identified by `trainerId`, and `_TRAINER_FROM` joins nothing — both halves are load-bearing.** `trainerId` and `trainerName` are non-NULL on all 314,981 rows and every id maps to exactly one name, but 4,665 ids carry only 4,630 distinct names: 35 names belong to two different people, so grouping on the name reports one career for two. And joining `archive.horse` the way the horse subject must would silently drop the **27,430 non-absent rows `RECOMPUTE_HEPPA_START_HORSEKEY` never reached** — 9% of them, starts the trainer really had, and whole trainers whose every start is one of them (365 observed on one id). Nothing needs that table: `hs.horseName` is on the row, and it leads the trainer drill-down's eleven columns. The trainer search is deliberately **one**-stage, unlike the horse's: one id is one trainer, so there is no canonicalisation to resolve; its `horses`/`years` columns exist only as the disambiguator the 35 shared names force, and **the parentheses around its `OR` are load-bearing** — without them the absent filter binds to the id arm alone and a pasted id lists withdrawals.

  **A driver is identified by `driverId`, and `_DRIVER_FROM` is `_TRAINER_FROM` with one column changed** — same missing join, same reason. `driverId` is non-NULL on all 298,492 non-absent rows and carries 3,196 distinct ids, and **zero of them carry two different first+last names**, while 6 full names are shared by two ids — so the subject is keyed on the id and only the *bucket label* merges those six, which the drill-down merges identically. **`driverName` is not the column for either job**: it is the short form ('S Raitala') and 129 ids carry more than one, so Santtu Raitala's 9,256 starts include one reading 'V Stenman'. `SQL_SEARCH_DRIVERS` is `SQL_SEARCH_TRAINERS`'s shape line for line — one stage, the same `horses`/`years` disambiguators, the same load-bearing parentheses, the same `(term, term, limit)` — differing only in matching and displaying `driverFirstName || ' ' || driverLastName`, because matching the short form *as well* would need a third `?` and break the parameter contract `search()` relies on for every subject.

  **The counterpart-role axis is whichever role the subject is not, and it is one of two capped breakdowns.** A horse gets `HORSE_DRIVERS`, a trainer `TRAINER_DRIVERS`, a driver `DRIVER_TRAINERS` — asking a driver which drivers drove it returns one row equal to Overall. **There is one axis per subject rather than one per role**, because the axis is a per-`Subject` field and nothing forces the three to agree. All three cap at 5 today, which is a decision rather than a coincidence: a top 3 cut a majority of every subject — 56.1 % of horses have more than 3 drivers and 38.6 % more than 5 (median 4, mean 5.5, max 35). `_partner()` builds all three, so changing one is one line. The driver label is `driverFirstName || ' ' || driverLastName`, not either column that looks more like an identity: `driverName` is the short form and unreliable — 129 ids carry a second, *different* person's short name on a handful of rows, so Santtu Raitala's 9,256 starts include one reading `'V Stenman'` — and `driverId` is clean (zero ids carry more than one first+last name) but is 19 digits, and a bucket label is read. The full name is non-NULL and never partial on any of the 298,492 non-absent rows, so no `coalesce`; 3,190 distinct values against 3,196 ids means 6 names belong to two people and merge into one bucket, which the drill-down merges identically. The trainer label is plain `trainerName`, which unlike the driver's *is* already a full name: 4,656 ids carry 4,620 distinct names, so 36 names merge the same way. `limit` caps **`breakdown` only** — `starts` stays uncapped, so a bucket on screen still opens exactly its count, and a role cut by the cap is still reachable. Coverage says the same as the counts: for a horse 3 drivers cover 79.5% of the starts and **5 cover 88.8%**; for a trainer 75.1% and **83.9%** (mean 7.9 drivers per trainer, max 131); for a driver 3 trainers cover only 52.5% and **5 cover 57.9%**, because a driver has a median of 2 trainers but a maximum of 922 and the busy drivers carry the rows. **Those horse figures are grouped on `canonicalKey`, which is what `_HORSE_FROM` joins for** — grouping on `horseKey` reads 72.5%/81.2% instead, because the 182 horses split across 365 keys are then counted as separate, shorter careers. Measure this the way the axis runs, not the way the table stores. So these do not sum back to Overall; the titles say so, and the sum-back test asserts the exemption off `one.limit` rather than off a title — which is what made the second capped axis free to add. `, driver`/`, trainer` breaks the ties — 970 trainers have a starts tie straddling the third and fourth driver.

  **Post position is counted per start type, because the bare number averages two opposite questions.** Off an auto the field lines up abreast and the inside is a shorter trip; off a volt they turn in from a standing tier, where the inside is traffic. The archive says so plainly — win rate by post, non-absent: auto peaks at post 4-5 (13.0%, 12.9%) while volt peaks at post 1 (15.4%) and falls monotonically to 8.4% by post 4, so a merged bucket 4 reports a figure describing neither. Merging also hides the ranges: post 12 has 6,479 auto starts against 386 volt ones. **`startTrack = 0` is 'not reported', not a post**, and it collapses into one `unknown` bucket rather than `auto 0`/`volt 0` — two rows saying one thing, sorting ahead of post 1 as if further inside. It is 87 non-absent rows, every one `finnishTrack = false`: a programme abroad that does not name the post. The column is NULL on **zero** rows of the whole table, so that guard is construction and not data — but `||` propagates a NULL and a NULL label is a bucket that opens nothing. The sort key is the type's rank × 100 + the post, safe because the posts run 1-16, and it is passed as both `order` and `sort` so it reaches GROUP BY/ORDER BY without landing in the SELECT list. Uncapped, so it sums back: 9 buckets for a median horse, 31 for the busiest trainer.

  **The track axis groups on `hs.trackCode`, and a name was measured and rejected.** `archive.heppa_start` has no name column; `archive.heppa_event` has one, but a LEFT JOIN on (meetDate, trackCode) leaves **3,648 non-absent starts nameless and resolves only 52 of the 99 codes** — the local, pony and foreign meetings have no event row — while an inner join would drop those starts outright, the same trap `_TRAINER_FROM` exists to avoid. That column is the organisation's name in any case (`Vermon Ravirata Oy`), not a track's. The code is also the drill-down's `trk`, so bucket and start list share one vocabulary, and no `coalesce` is needed because `trackCode` is in the primary key. Capped at 5 — 99 codes archive-wide, a median of 7 tracks per horse (max 30), 8 per trainer (max 47) and 5 per driver (max 46) — with the cap in the title for the same reason the counterpart role's is. **It ranks by wins, not by starts**, because the busiest track is not the one a subject is good at, and it falls back to starts to fill the rest: `"1st" DESC, starts DESC, track`, ordering on the output alias so there is one definition of what a win is. **That fallback is the normal case rather than an edge case**, which is why the title names it — a subject wins at a median of 1 track (a horse or a trainer) or **0** (a driver), and 89.6% of horses, 80.5% of trainers and 84.0% of drivers win at fewer than 5 — so for most subjects most of this table is the fallback, where every winless track ties at 0 and `starts DESC` ranks it.

  **`startInterval` bucketing means something subtly different per subject.** The gap is always the *horse's* own, which is a fair trainer question, but the "NULL collapses to one row per horse" argument below **is conditional on the horse subject**: with no join, a trainer's unknown bucket mixes each of its horses' earliest starts with the no-identity rows, and is no longer at most one row. The label string is right for a horse and two tests pin it, so the caveat lives in the `LEGEND` instead. **The label expression that names an axis's buckets is written once**, and both queries are generated from it: `axis.breakdown` groups on it, `axis.starts` filters on it with `= ?` to list the individual starts behind a clicked bucket. Two copies would be two definitions of what `'<= 14 days'` means, free to drift — the reason `crosscheck` builds on `HEPPA_START_BRIDGE` rather than a lookalike. Verified over the 400 busiest horses and all 6,507 of their buckets, and again over the 20 busiest of each subject and all 832 of theirs after the seam went in: a bucket's drill-down returns exactly the count the bucket showed. **Every label is non-NULL by construction, and that is a requirement**: `NULL = ?` is never true, so a NULL label would be a blank row that opens an empty list — hence the `coalesce` around the shoe concatenation, where `||` propagates a NULL, and around `specialCart`. Both are NULL on zero archive rows today, which is data rather than construction. `Overall` has no label at all, so clicking it lists every start. **`absent` rows are excluded in every query**: a withdrawn entry carries shoes and a cart, because entry data is what the registry holds at that point, but never a placement or a `startInterval`, so counting one invents a shoe combination the horse never raced in. The **horse** search is deliberately **two-stage** — a CTE resolves the term to `canonicalKey`s, then the outer query re-joins every `horseKey` of each. Filtering and grouping in one pass restricts the join to the *matched* rows, so a term matching a non-canonical name variant reports a horse that has starts as having none: `humble stance fr` returns 0 starts one-stage and 2 two-stage. The drill-down's `ORDER BY` ends in `programNumber` because a trainer can have two horses in one race, which made the old `(meetDate, raceNumber)` order non-total; it is a no-op for a horse.
- The drill-down's start list is compact on purpose — date, track, race, distance, lane, placing, km time, odds, prize, driver — and its placing column is `coalesce(cast(placement as varchar), disqualifiedCode, '-')`. `heppa_start.placement` is NULL on 36,054 of the 293,843 non-absent rows, so a bare column would render one start in eight as a blank cell, which reads as data we do not have rather than as what happened: a disqualification shows its code (`hpl`, `hll`, `k`, `hlo`) and a start that finished outside the placings shows `-`. Ordered newest first, `raceNumber DESC` within a card, because heats and a final sit on one day. Its last three columns each have a different missing-value story, and the SQL treats them differently: `lane` is `startTrack`, the post, 1-16 and never NULL at a Finnish meeting — **but 0 at some meetings abroad**, where the foreign programme's post is not recorded (87 non-absent rows now, every one `finnishTrack = false`), so a 0 there reads 'not reported' rather than a post position, and the post-position axis buckets exactly those rows as `unknown`; `prize` is `prizeWon` in euros and also never NULL, where **0 is what an unplaced start won** — a fact, not a gap, on 128,262 rows; and `odds` is `winOdd` out of hundredths, NULL on the 44,995 local and pony starts with no betting, with `nullif` blanking the 64 rows that store 0, since 1.00 is the floor of a win odd and a zero there means 'not reported'. `printf('%.2f', …)` rather than `round()`, which returns a double and prints a 2.60 price as 2.6, and which would also have to be told what to do with the NULLs.
- `horse_tui.py` — the Textual app (`StatsApp`) and the `stats` CLI handler; widgets only, no SQL. **Which subject is on screen is app state, not a third app**: `t` cycles horse → trainer → driver and re-runs the term rather than clearing, which is what makes `veikkaus stats 'koivunen'` — no horse by that name — one keypress from the three trainers and a second from the four drivers. The widget tree never changes, because `horse_stats.breakdowns` is always `AXIS_COUNT` long: a cycle **retitles** the panels (`#bt{i}`) and rebinds each table's `axis`, which `show_subject` does on every path that fills the screen and `_retitle` does on the two that do not — a cycle with an empty search box, and a term matching nothing. Only the table contents and the hit columns change otherwise, and `clear(columns=True)` already handled that. **Focus leaves the search box even when a term matches nothing**, and that one line is what makes the cycle usable: an `Input` swallows every printable key, so before it `t` typed a `t` into the term instead of switching subject — in exactly the state the cycle exists for, since 'no horse called koivunen' is precisely when the next keypress is meant to be `t`. `/` and escape come back to the box, as they do from a hit list. The heading is `name · identity — N starts` for both, because a name is what you searched for while a `trainerId` is 19 digits, and the identity is what every other tool here speaks. `StartsScreen` fills with `add_rows` rather than a row at a time: Overall on the busiest trainer is 3,701 starts over eleven columns. Reads through `db_read` **per query, not per session**, so a browsing session cannot hold the archive against a concurrent `parse` (verified: a read-write open from another process succeeds while the UI is idle). Each breakdown runs inside its own `try`, so a column an older archive lacks costs that one panel instead of the screen. **Every DataTable here is a `GuardedTable`, because the framework crashes on a click into an emptied one.** `DataTable._on_click` treats any click at row -1 as a header click and reads `ordered_columns[column_index]` without checking there are columns, so a click anywhere in a table `clear(columns=True)` emptied raises IndexError out of textual and takes the app down — reproduced on 8.2.8 by searching for a term that matches nothing and clicking either the hit list or any panel. Its own out-of-bounds guard is skipped whenever `cursor_type` is `'row'`, which is what every table here uses, so it never fires. The fix is `event.prevent_default()`, **not a plain return**: textual dispatches an event to the handler in *every* class of the MRO, so `DataTable._on_click` runs after ours and cannot be overridden away — defining `_on_click` would not replace it and would kill our own handler too, since a class contributes `_on_click` *or* `on_click` and the underscore wins. `prevent_default` sets the `_no_default_action` flag `_get_dispatch_methods` breaks its MRO walk on. `ClickableTable` subclasses it and supplies `_clicked` rather than a second `on_click`, so the guard has one definition. **The click path is a `DataTable` subclass, and every part of that is counter-intuitive.** A single click on a `cursor_type='row'` table posts only `RowHighlighted` — `RowSelected` wants a second click on the same cell — and `DataTable._on_click` calls `event.stop()`, so an app-level `@on(events.Click)` never fires. `ClickableTable.on_click` therefore reads the clicked row from `event.style.meta['row']` (the header is -1, a click below the last row has no `row`, and `self.cursor_row` is still the *old* row there). It posts its **own** message rather than reposting `RowSelected`: `_on_click` posts that itself whenever the clicked cell already holds the cursor, which a freshly filled table's (0, 0) always does, so a `RowSelected` handler opens two panels for one click on the first row — observed, and only on that row. Enter is a subclass binding for the same reason, replacing DataTable's own (bindings merge with the most-derived class winning per key), so mouse and keyboard have exactly one path each. The bucket label rides in the row key, as the hit list's identity does — a `canonicalKey`, a `trainerId` or a `driverId`, paired with its display name in `self.labels` because the id is not readable. `StartsScreen` uses `DEFAULT_CSS`, which is auto-scoped, not `CSS`, which is global and would restyle the tables underneath, and it rebinds `q` to close so the reflex does not quit the app.

**`archive.leg_percentage` is shaped around one asymmetry: these figures are final, where `odds_snapshot`'s are a history.** One row per **(poolId, legNumber, startNumber)** — `capturedAt` is deliberately *not* in the key, unlike `odds_snapshot`, where it is. The win pool is crawled for its movement, many snapshots of one pool; a T-pool's percentages are wanted closing, so a re-fetch of a pool crawled while betting was still open **replaces** the row rather than accumulating a second version beside it, and `--refetch-from` is how that is done. The full crawl is in: **3,182 pools fetched with no failures and 178,175 rows loaded, 2021-01-01 to 2026-08-11**; the never-run legs were then dropped (below), leaving **176,402 rows over 3,148 pools, 12,906 races and 146,320 runners** — T4 1,327 pools/60,868 rows, T5 1,114/62,728, T75 362/30,296, T65 336/21,896, T64 9/614. `percentage` is hundredths of a percent and sums to ~10000 per leg — **none of the 15,482 legs falls outside 9,990-10,010** — and `percentage`, `runnerId`, `capturedAt` and `netSales` are NULL on zero rows; `amount` is the money on that runner in that leg and the payload's `ticks` is its exact twin on every row of every payload checked, so only one is stored. `netSales`/`netPool` are **pool-level and repeat on every row of the pool**, as `poolType` does on `odds_snapshot` — aggregate them per pool, never over rows. `scratched` is **TRUE or NULL and never FALSE** — the payload sends the key only where it is set, 10,995 true against 0 false and 165,407 absent — so it is a flag, and absence is stored NULL rather than folded to FALSE, which would read as the payload having said so. **A scratched runner keeps the money that was bet on it before the withdrawal**: percentages up to 7,183 (71.83 % of a leg), and they still count into the leg's ~10000, so a model reading these as pre-race support must decide what a withdrawn runner's share means rather than assume it is ~0. It is also the *more current* of the two scratched columns, on the known asymmetry: the Veikkaus runners payload is entry data, so a horse withdrawn at the track is not marked there.

**72 of the 3,148 pools sit on the combination-pool meta-cards, and those rows need the same exclusion `recompute_cross_source_intervals()` makes.** `MM` 64 pools/3,379 rows, `Sl` 7/516, `T75` 1/80 (trackNumber 48/88), against 3,075 pools/172,361 rows at 44 real tracks and one Swedish simulcast pool. **The pools themselves are real and distinct** — no pool spans both kinds, each has its own `netSales`, and a Magic Monday T4 is a genuine cross-track combination pool: sample pool 7743581's four legs match Oulu races 6-7 and Teivo races 6-7 exactly on `startTime`. What is duplicated is the *race*, because a meta-card re-lists races that also run under their real track, so these rows carry the meta-card's copy of `raceId`/`startNumber`. Two consequences: joining a horse's real start to its percentages **misses** them, and grouping percentages by card double-counts the race. **One pool of the 3,182 produced no rows at all** — a T4 on the `MM` card of 2022-01-24 with `netSales` 0 and an empty `odds` list, a pool that took no money. Nothing was dropped: there was nothing to store. The table joins `archive.start` on either `runnerId` or `(raceId, startNumber)`, verified equivalent over the whole crawl — 176,387 of 176,402 rows match, and **all 15 that do not are vacated start numbers**: `scratched`, `percentage` 0, and no `archive.start` row because `is_placeholder()` drops the `Poissa` runner that stood there. So a non-joining row is a start number with no horse, not a bridge fault. **A runner can appear in more than one pool** — 31,743 in two and 56 in three, because one race is often a leg of both the T4 and the T5 — which is why the key is (pool, leg, runner) and not (race, runner); `runnerId` is what `archive.bet_percentage` keys on, so the single-race and multi-leg percentages of one runner meet there.

**`leg_percentage.placement` is what makes the percentages answerable, and it is stamped rather than joined** (`ArchiveDb.recompute_leg_placements()`, in `parse_all()` **after** `recompute_start_from_heppa()`). The percentages say where the money went; the question they exist for is how the money *did*, and re-deriving that per query invites the mistake it is easiest to make here — a window function placed after the winner filter sees a one-row partition and calls every winner the favourite. So the finish is written onto the row once, and a statistic is a `GROUP BY`.

It holds **the payout order**, `archive.start.placement`, because this is a betting question and that is the order the pool paid on: Veikkaus wins the merge's coalesce, so on the 16 races where a post-race disqualification moved the result this differs from `heppa_start.placement`, which keeps the official one. **The join is `(raceId, startNumber)`, not the Heppa bridge**, and that is what keeps the 72 meta-card pools working — a meta-card has no Heppa event by design, yet all 370 of its legs are placed. The ordering after the merge is load-bearing: 100,057 of the 147,098 placed rows come from Heppa, because **56 % of leg rows finished 4th or worse** and Veikkaus never publishes those. Run it first and the column is 1st-to-3rd only. `RESET_LEG_PLACEMENT` blanks the column before each pass for the reason `start_record()` writes its derived columns NULL: a re-crawl that removes a result must not leave the old placement behind.

**A leg no runner of which was placed first is a race that never ran, and those are dropped** (`DROP_UNRUN_LEGS`). That was 1,773 rows over **33 pools, every one of them whole**: 139 of the 144 races sit on 28 meetings Heppa flags `canceled` (`trackCondition` and `temperature` NULL beside it), and the other five are one card abandoned after race 3 — Lahti 2023-11-02, at -2 °C, where Heppa rightly records the meeting itself as `canceled = FALSE` because it took place. Verified independently: **not one `prev_start` row names those (date, track) pairs**, against 208 for the days before them. **`archive.race.raceStatus` is no help** — it reads `OFFICIAL` on all 262 races of the canceled cards, so Heppa's flag is the only honest signal. The money was real and was refunded; what is gone is pools for meetings that did not happen.

The delete is at **leg grain, not pool grain**, though nothing in the archive straddles yet: a meeting abandoned mid-card could leave a pool with some legs run and some not, and dropping only the unrun ones is right there — percentages are per leg, so each surviving leg still sums to ~10000, and such a pool would then show fewer legs than its product name implies. **Nothing is lost**, which is what makes a delete acceptable at all: the raw payloads stay, `parse --full` re-inserts every dropped row, and the rule re-runs on every parse — so a card crawled before its results were published, which the two-day `--to` lag exists to prevent, is recovered rather than lost.

What it buys is an invariant worth relying on: **every leg in the table has a winner**, 15,482 of them, 15,500 winner rows. The 18 extra are **dead heats** — Oulu 2021-02-06 race 9 has Jamir and Evartti both `placingRaw '1'` in both sources and nothing placed second — so count winners with `count(*) FILTER (WHERE placement = 1)` and never join on the assumption of exactly one per leg. The money is well calibrated against it: by percentage bucket the win rate runs 1.0 %, 3.9 %, 7.9 %, 15.2 %, 26.6 %, 42.5 %, 66.3 %, and the leg favourite wins **41.3 %** of the time.

**`start` vs `prev_start` — the distinction that matters most here.** `archive.start` is one row per (race, horse) built from the runners payload: it describes *the race*, and its `placement`/`kmTime` stop at the paid places because that is all the results endpoint publishes. `archive.prev_start` is built from `runner.prevStarts` — the horse's own career line riding along inside the same payload — and it describes *the careers*: a finishing position for the whole field (observed to 16th), km time, win odd, driver, track, distance and post, per earlier start. It carries `horseKey` rather than the reporting `runnerId`, and is keyed on **(horseKey, meetDate, raceNumber)** — the natural identity of a start.

**Do not key it on `priorStartId`.** That id is assigned per reporting payload, not per start: when a horse races again its whole prevStarts list comes back renumbered as a fresh contiguous block (observed as a constant +1,271,073 offset between two reports of one career). Keying on it stores the same career once per race the horse subsequently ran, and feeds `startInterval` a zero-day gap between each copy. This was shipped and then fixed; the regression tests in `tests/test_archive_db.py` pin it. `raceNumber` belongs in the key because heats and finals put a horse in two races on one card — those are real rows with a genuine zero-day gap.

`prev_start.trackCode` shares a vocabulary with `card.trackAbbreviation`, so the two join on (meetDate, track, raceNumber) — verified against directly-crawled results, which agreed on every overlapping placing.

**`startInterval` is filled in after loading, not per record** (`ArchiveDb.recompute_start_intervals()`, called at the end of `parse_all()`). A reported prevStarts list is a truncated ~8-entry window, so the gap in front of its oldest entry is unknowable from that list alone; and because the window slides forward, whichever report landed last would otherwise decide the stored value. Recomputing over the accumulated table with a window function per `horseKey` makes it deterministic, and re-derives correctly as more dates are crawled in. A horse's earliest start in the archive has no predecessor and keeps the old pipeline's epoch sentinel — **days since 1970-01-01, so it varies with the meet date (~19,600–20,700 observed), not a fixed number.** Filter it in analysis with a threshold well above any plausible gap (`startInterval > 10000`), never by equality. Exactly one row per horse carries it.

**`start.startInterval` and `heppa_start.startInterval` answer a different question, and disagree with `prev_start`'s on purpose** (`ArchiveDb.recompute_cross_source_intervals()`, last in `parse_all()`). `prev_start`'s is a window over `prev_start` alone, partitioned by `horseKey`, with the epoch sentinel on a horse's first row. These two are a window over the **union of all three start-bearing tables**, deduped per horse per `(meetDate, raceNumber)`, partitioned by **`canonicalKey`**, and **NULL** where no predecessor is known — so **never filter them with `startInterval > 10000`; use `IS NULL`.** It must run *after* `recompute_heppa_links()`, which is what writes `canonicalKey` and `heppa_start.horseKey`; run it first and the column comes out almost entirely NULL with no error anywhere.

Three things it does that `prev_start`'s does not. It partitions on `canonicalKey`, because the 182 horses split across 365 keys would otherwise get one inflated career per name variant. It excludes non-runners, by a vote: `archive.start` offers `NOT scratched`, `heppa_start` offers `NOT absent`, `prev_start` **abstains** (it only supplies a date), and a start counts only when every source with an opinion agrees the horse ran. And it counts qualifying starts (`kl`) and retirements (`k`) — the horse went to the gate, which is what a layoff measures; `prev_start.result` filters them downstream.

**The combination-pool meta-cards are excluded from the union, and that was the whole ball game.** `MM`, `Sl`, `T75`, `KUN`, `JAA` and `CIT` (trackNumber 48/88) are not meetings — a meta-card re-lists races that also run under their real track, so counting one puts the horse at two tracks on one day and hands the *next* real start a zero-day gap. Before the filter, 2,514 horse-days were spread over more than one track (2,489 of them a meta-card) and **2,475 of 2,806 zero-day gaps on `archive.start` were spurious**; after it, 356 remain. Dropping them costs almost nothing: of 2,712 meta-card start rows, 8 are the only appearance their horse has that day. **The Swedish simulcasts (trackNumber 57/87, abbreviation ending `-V`) are deliberately kept** — the other card with no Heppa counterpart, but a real race the horse really ran, duplicating nothing, and responsible for 0 multi-track days. Dropping those would inflate the gaps around them.

**`archive.start.scratched = FALSE` and `startInterval IS NULL` can both be true on one row**, and that is the trap most likely to confuse a reader. The runners payload is entry data, so the 175 starts a horse was withdrawn from at the track are not marked there; the vote excludes them from the timeline without laundering `scratched`, which still means "scratched as of entry, per Veikkaus". Every NULL on `archive.start` is one of exactly four things, and they add up: 18,999 scratched, 10,886 a horse's earliest known start, 2,664 a meta-card row, 175 Heppa-`absent` — 32,724 of 288,519, leaving 255,795 filled. On `heppa_start`, **NULL has a fifth meaning: no identity** (29,083 rows `RECOMPUTE_HEPPA_START_HORSEKEY` never reached), so the query that separates the two is `WHERE horseKey IS NOT NULL AND startInterval IS NULL`. **Per horse those five collapse to one**: exclude `absent` and the no-identity rows cannot be joined to a horse at all, so a NULL on a horse's own `heppa_start` rows means exactly "no earlier start known" — at most one row per horse, which is why `horse_stats` gives it its own bucket rather than folding it into the shortest one.

Measured over the 13,666-row overlap with `prev_start`: 12,123 agree, 1,441 replace the epoch sentinel with a real predecessor, 97 are *shorter* because a Heppa-only local meeting or a name-variant of the same horse sits inside the gap, 9 are newly NULL — and exactly **1 is longer**. That one is not a violation: `haahuilee|2021` was entered at Kouvola on 2026-07-29 and withdrawn (Heppa `absent`, `prev_start.result` NULL), so its true layoff into 2026-08-03 is 24 days and not `prev_start`'s 5. The invariant is therefore *a gap may only grow where a non-runner was excluded* — the loose form, "a union can only add predecessors", is wrong, because this union also removes.

**The starts abroad moved these figures, and the direction was the predicted one.** A gap can only shrink where a start inside it was previously unknown, so zero-day gaps cannot appear — a horse cannot be in two places on one day. Measured after the full foreign crawl: **zero-day gaps on `archive.start` are still exactly 356**, unchanged, and `archive.start`'s NULLs went 32,724 → **32,534 of 288,850**. On `heppa_start` the two NULL meanings now read **30,551 with no predecessor and 29,670 with no identity** (the second grew by the 560 foreign rows `RECOMPUTE_HEPPA_START_HORSEKEY` could not resolve). **3,266 home starts have a start abroad inside their preceding 90 days**, which is the population whose layoff this changed. Combat Fighter is the shape of it: its 2026-06-20 start read 35 days and now reads 21, with the Solvalla start of 2026-05-30 sitting between. Note `archive.start`'s *total* also moved, 288,519 → 288,850, for reasons predating this — Veikkaus crawling, not the foreign starts, which add no rows to that table. **The join-back that writes the column must use all five primary-key columns**, `horseId` included: every foreign start in a race is `programNumber` 0, so a four-column match covers the whole race and `UPDATE ... FROM` then hands horses each other's layoffs. That shipped briefly and is pinned by a regression test.

**Two residues, both known.** 25 of the 356 remaining zero-day gaps are one malformed card: Veikkaus's Teivo card for 2023-11-07 carries races 9 and 10, which Heppa's Tampere meeting (races 1-8 and 21) does not have and whose horses Heppa places at Pori that day. Everything else with a zero-day gap has its predecessor on the same card, which is the heats-and-finals case and genuine. A *third* residue appearing means something new, exactly as with the two Heppa-less cards above.

**Heppa is where the finishing order actually comes from.** `archive.heppa_start` is one row per (race, horse) from Suomen Hippos's registry, keyed on **(meetDate, trackCode, raceNumber, programNumber, horseId)** — Heppa exposes no equivalent of `cardId` or `raceId`. It carries a placing for the whole field, for every Finnish meeting, in every year, without `prev_start`'s condition that the horse raced again. It also carries this race's prize money, a disqualification code per start, and stable registry ids.

**It is no longer Finnish-only, and that is why `horseId` is in the key.** `heppa-foreign` fills in the starts Finnish horses made abroad, and Heppa numbers every one of those `programNumber` **0** — Bollnäs 2026-08-16 race 8 really does return five Finnish horses, all `0`. Without `horseId` the four-column key collides and the loss is *silent*: `_insert_many` dedupes within a batch on `HEPPA_START_KEY` and `INSERT OR REPLACE` dedupes across them, so four of those five simply would not be there. `horseId` is non-NULL on all 314,981 rows the archive held before the change and `programNumber = 0` on none of them, so both halves are safe. **`finnishTrack` is the column that marks a row as a start abroad**, and it is what separates the two populations in every downstream query — `coalesce(finnishTrack, true)` where an older archive might have NULLs.

**An archive predating this is rebuilt once, by `archive_db.migrate_heppa_start_pk()`**, called from `create()` between `ADD_COLUMNS` and `CREATE_INDEXES` — both sides of that matter, because the rebuild copies every column and DuckDB refuses to rename a table an index depends on. It preserves every row and stamps `finnishTrack = TRUE` on them, which is a fact and not a default: every pre-existing row descends from a `heppa_results` event, and that listing is Finnish-only. So **no re-parse is needed**. The one thing it cannot carry over is a row with no `horseId` — the new key will not hold a NULL — so those are dropped with a printed count; there were none in practice, and `parse` now drops them at the door for the same reason.

The bridge between the two sources is **positional, never name-based**: `(card.meetDate, heppa_track_code(card), race.number, start.startNumber)` against `(meetDate, trackCode, raceNumber, programNumber)`. Matching on horse names instead would break on the country tag Veikkaus appends and Heppa keeps in a separate field. Cards that do not match are the Swedish simulcasts (abbreviation ending `-V`, trackNumber 57/87) and the Veikkaus combination-pool meta-cards (`MM`, `KUN`, `CIT`, `T75`, `Sl`, `JAA`, trackNumber 48/88) — neither is a real meeting and neither has a Heppa counterpart by design. The bridge needs no change for the starts abroad: it joins `start.startNumber` to `programNumber`, a Veikkaus start number is ≥ 1, and a foreign row's is 0, so it cannot match anything. **`crosscheck` does need one**: its unmatched-meeting report filters `finnishTrack`, because a meeting abroad has no Veikkaus card *by design* — that is why it was crawled at all — and 356 of them would drown the vocabulary gap the report exists to catch. They get their own report instead, `Starts abroad: what the foreign crawl reached`, where `horse_resolved` is legitimately short of every row: the horseId→horseKey mapping is built from races both sources cover, so a horse whose Finnish starts fall outside the Veikkaus crawl has no `archive.horse` row to resolve to (17 of 19 at Bollnäs, 8 of 12 at Täby).

**`heppa_track_code()`, not bare `upper()`.** Upper-casing gets every real Finnish track right — Veikkaus writes `Ku`, `Tk`, `Jo`, Heppa writes `KU`, `TK`, `JO` — with one exception that cost 28 meetings before it was caught: **Veikkaus spells Härmä both `Hr` and `Hr2`** (Härmä Powerpark and Härmä, both trackNumber 37) and Heppa has only `HR`, so `Hr2` upper-cased to `HR2` and matched nothing. Verified before aliasing: 28 `Hr2` cards, 28 otherwise-unmatched `HR` meetings, the same 28 dates, nothing left over either side, and `Hr` and `Hr2` never share a date. `HEPPA_TRACK_ALIASES` holds it as an explicit alias rather than a rule like "strip trailing digits" — this is one operator's vocabulary quirk, not a pattern. Note the check that missed it originally asked whether two *cards* collide on `(date, upper(abbreviation))`; it never asked whether `Hr2` resolved at all. `crosscheck` now reports unmatched cards grouped by track, where a whole track showing up is the signal.

**The merge into `archive.start` is three statements, and all three are load-bearing** (`recompute_start_from_heppa()`). The obvious single `UPDATE` is not idempotent: it reads `s.placement` to decide `resultSource` and writes `s.placement` in the same statement, so a second run sees Heppa's own fill and relabels it `'veikkaus'`. Instead: reset what Heppa previously contributed (which `resultSource` identifies), merge with `coalesce` so Veikkaus never gets overwritten, then label the remaining placements `'veikkaus'`. That is also why the merge stays away from `winOddsFinal` — one provenance marker cannot honestly describe two columns that can come from different sources on the same row, and the odds history is Veikkaus's anyway. `parse_all()` happens to rebuild `archive.start` from the raw zone first, which would mask the problem; a recompute whose answer depends on how often it has run is a trap regardless.

**Horse identity is resolved through the registry, in both directions** (`recompute_heppa_links()`). `RECOMPUTE_HEPPA_HORSE_ID` fills `archive.horse.heppaHorseId` from the races both sources cover; `RECOMPUTE_HEPPA_START_HORSEKEY` reads that mapping back to stamp `horseKey` onto Heppa rows — including the local and pony meetings, where there is no `archive.start` row to join to. It has to go through `horseId` because **a Heppa start carries no birth year**, so `horse_key()` cannot be computed from one.

**Where the two sources genuinely disagree, and what `start.placement` therefore means.** Over the 73,161 starts both sources place, they agree on 73,145. The exceptions are all explained and none is a bug:

- **16 are post-race disqualifications.** Veikkaus records the order a pool *paid out on*; Heppa records the *official* order after protest. Mikkeli 2021-07-17 race 7 is the shape of it — Veikkaus has Pippi Roc 1st, Heppa has it `hyl` with the whole field promoted a place. Because the merge coalesces and Veikkaus wins, **`archive.start.placement` holds the payout order on those rows**; the corrected order is in `heppa_start.placement`. Which is right depends on whether you are modelling the market or the racing.
- **106 km times differ by exactly a tenth**, Veikkaus always the slower — a rounding convention, concentrated in 2024.
- **175 scratchings differ, and Heppa is right**: the Veikkaus runners payload is entry data, so a horse withdrawn at the track is not marked, while Heppa records it `absent`.
- **~50,000 horse names differ, all but one because of the country tag** — Veikkaus appends `(SE)`, Heppa keeps it in `horseRegistrationCountry`. The one exception is `Black Swan*` vs `Black Swan N`, the same horse under the two naming conventions. This is why the bridge is positional.

**Two real Finnish cards have no Heppa event at all** and never will from this crawl: Vermo 2025-08-16 and Kaustinen 2024-03-24. They are the entire residue of the track-vocabulary investigation — everything else resolved once `Hr2` was aliased — so a third appearing in `crosscheck` means something new, not this.

**`horseKey` joins; `canonicalKey` identifies.** `horse_key()` is name + birth year, and Veikkaus writes an import's name inconsistently — `Humble Stance`, `Humble Stance* (FR)` and `Humble Stance FR* (FR)` are one horse — which split **182 horses across 365 keys**. `RECOMPUTE_HORSE_IDENTITY` groups on `coalesce(heppaHorseId, baseKey, horseKey)` and writes the representative into `archive.horse.canonicalKey`. Every other table still joins on `horseKey`, which is all a Veikkaus payload can produce; **analysis wanting one row per horse must group on `canonicalKey`.**

The ordering inside that coalesce is the whole design. **Names never repeat within an origin country, but they do repeat across countries** — `Elliot` and `Elliot (DK)`, both foaled 2016, are two real horses, and the tag is the only thing separating them. Letting the registry id decide first means the name fallback never gets the chance to merge them; `baseKey` only carries horses the registry never reached (~31 %, mostly pony racing). Note `heppa_start.horseRegistrationCountry` is *not* the field for this — it says where a horse races, and reads `FI` for both Elliots. Origin lives in `/horse/{id}`'s `birthCountry`, which is not crawled.

**`strip_import_markers()` is deliberately conservative.** It drops a parenthesised country tag, and the trailing country letter of the Nordic import convention (`Morell S (SE)`, `Black Swan N (NO)`, `Harley D (DE)`) — but *only when that token agrees with the tag*, being equal to it or its first letter. Trailing tokens are far more often stable suffixes that belong to the name: `Birbone OK (IT)`, `Vulcano OP (IT)`, `Remington XO`, `Aurelia's Pearl KS`, `Tako ÖK* (NO)`. Stripping a trailing letter unconditionally would merge horses that merely share a stem. A token with no tag to agree with is kept, so `Pompom S*` stays distinct from `Pompom* (SE)` here — that pair is one horse, but the registry id says so, not this function.

**DuckDB rules.** Every id and epoch-millisecond value is `BIGINT` (`INTEGER` is 32-bit and `raceId`/`startTime` overflow it). Every table upserts with `INSERT OR REPLACE` — the SQLite `ON CONFLICT` clause inside a `PRIMARY KEY` definition is not supported. `_insert_many()` skips empty batches, which DuckDB's `executemany` rejects, and collapses duplicates *within* a batch against the matching `*_KEY` column positions, so the winning row is chosen in Python rather than by DuckDB's per-statement conflict handling — last row for a key wins, matching the SQL. Keep each `*_KEY` in sync with its table's `PRIMARY KEY` when columns move. Column order in the `*_record()` builders in `parse.py` must stay in sync with the matching `INSERT_*` in `archive_db.py`.

**API facts the schema is shaped around**, all verified in Phase 0 and all easy to get wrong:

- **A runners payload never carries result fields for its own race**, in any era. Placings come from `race.toteResultString` (which names the placed start numbers even when a pool paid fewer than three) with `/race/{raceId}/results` adding km time and the final win odd for the paid places only — so `archive.start.placement` is NULL past third. The full order is recovered from `prev_start` instead, retrospectively.
- **Prev-start `meetDate` is midnight Finnish time expressed in UTC**, so its UTC date is a day early on every row. Parse the meet date from `shortMeetDate` (`dd.mm.yy`) — that is what `parse_meet_date()` does, and it is what lines up with `card.meetDate`. Prev-start `winOdd` is a digit string in hundredths (`'1002'` = 10.02).
- **`prev_start.result` is a raw code**, kept verbatim: numeric placings alongside Finnish outcome codes (`kl` koelähtö, `k` keskeytti, `hpl`/`hll`/`hlo4` hylätty). `parse_result()` fills `placement` only for the numeric ones. Qualifying starts (`kl`, usually raceNumber > 20) are kept rather than filtered — `result` identifies them.
- **A prev-start entry carries no trainer.** It has `driver`/`driverFullName` and nothing else about the connections. `prev_start.coachName` is therefore *sourced from the archive*, not from the payload: `RECOMPUTE_PREV_START_COACH` fills it from the `archive.start` row for that same race, matched on (horseKey, meetDate, raceNumber), which recorded the trainer as of that day. Rows outside the crawl window stay NULL — there is no honest source for them. Never stamp the reporting runner's `coachName` onto these rows: that is the trainer at a *later* race, and with a start re-reported by every subsequent race it would be whichever report happened to land last. The old `main.start` table did exactly that. Track is deliberately not in the join — `prev_start.trackCode` and `card.trackAbbreviation` are not verified to share a vocabulary at every track, and a horse cannot be in two places on one day.
- **`runner.prize` is career earnings, not the race purse** (it equals `stats.total.winMoney`), hence the column name `careerWinnings`.
- **`placing` is a reserved word** in DuckDB's Postgres-derived parser, so the column is `placement`.
- **Km times drop the leading minute** — `'24,9a'` is 1.24,9 from an auto start, 84900 ms. Monté times take a leading `m` (`'m19,6'`); slower times spell the minute out (`'2.05,0'`).
- **`autoStart` comes from `race.startType`, not from the km-time suffix.** Start type is a property of the race, so it is known for every runner — including scratched horses and everyone outside the paid places, none of whom have a km time to read an `a` off. `recompute_auto_starts()` sets it from the race after loading; the suffix survives as a per-horse cross-check (the two agree exactly wherever both exist). Only `CAR_START`/`VOLT_START` have ever been observed and anything else is left NULL. `prev_start` has a `raceStartType` field but the API sends `UNKNOWN` in every entry, so there the suffix is the only per-row signal and the crawled race fills what it can.
- **Historical payloads are thinner than live ones**, and any field can go missing. Only the identifying fields are required — `Card.cardId`/`meetDate`, `Race.raceId`/`cardId`, and `Runner.runnerId`/`raceId`/`horseName`/`startNumber` — because a runner missing one of those cannot be placed at all. **Everything else is Optional on purpose, and tightening one back up trades a whole row for a cosmetic field**: a validation error drops the entire runner, with its start, horse, stats and career line. The API has taken that offer repeatedly (thin pre-2010 cards, absent breeding on a 2005 runner, a 2021 runner with no `coachNameInitials`). Schema drift then shows up as NULLs in the tables rather than as silently dropped rows. `stats` and `prevStarts` ride along only while a card is current, so `archive.stat` and `archive.prev_start` are empty for backfilled years — the career history accumulates from crawling *recent* dates, not old ones.
- **A vacated start number comes back as a `Poissa` ("absent") runner**, not as an omission: always `scratched`, no `coachName` key at all, `gender` usually `UNKNOWN`, and an arbitrary `horseAge` (0–24 across the 19 in the archive). `parse.is_placeholder()` drops them, because each would otherwise become a junk `archive.horse` row — one per distinct age, colliding across tracks and dates — plus an empty start. It tests the horse name and the missing `coachName`, never `driverName`, which arrives as `'Poissa'`, `'- -'`, `'Poissa Poissa'` or `''`.

**Horse identity.** `horse_key()` = `normalize(name)|birthYear`, where normalize folds case and spacing and drops the `*` marker but *keeps* a country tag such as `(SE)` — that tag is what separates an import from a same-named domestic horse. The Veikkaus API exposes no registration number; Hippos's Heppa registry is the authority, and `archive.horse.heppaHorseId` now carries it for the horses the crawl reaches. See `canonicalKey` above for how the two are combined — and note `horse_key()` itself is unchanged on purpose, because it is the only identity a Veikkaus payload can yield on its own.

**Heppa API facts**, all verified live and all easy to get wrong:

- **`startNumber` is the race number and `programNumber` is the horse's start number** — the exact inverse of the Veikkaus vocabulary.
- **Every scalar arrives as a string**, and `'-'` is a common "no value". The models type them `str`; `parse.py` converts. `horseId`/`driverId`/`trainerId` are 19-digit strings kept as `TEXT` — 8.37e18 was observed against a `BIGINT` ceiling of 9.22e18, and the margin is not worth the risk.
- **`placing` has three regimes**: `'0'` is no placing (absent, or disqualified under `hpl`/`hll`/`hrp`/`k`), `'1'`-`'13'` is a real placing, and **`'105'`/`'108'`/`'110'` is 100 + the position a disqualified horse crossed the line in**, always alongside `disqualifiedCode='hlo'`. `parse_placing()` fills `placement` only from the middle regime — the same treatment `parse_result()` gives `prev_start`'s `hlo4`, which encodes exactly the same thing. Filling it would put two horses in one position and break the placings-are-unique check of §8. The raw code survives in `placingRaw`. The column cannot be called `placing`: DuckDB reserves it, as for `archive.start.placement`.
- `disqualifiedCode` uses the same vocabulary as `prev_start.result`. `gallop` is orthogonal — a horse can gallop and still win.
- **`price` is this race's prize money; `horsePriceSum` is career earnings *including* this race.** Veikkaus's `careerWinnings` is the *pre*-race figure in cents. Verified: 142000 cents + 700 € = 2120 €. `horsePriceSum` and `record` therefore leak the result and must never become as-of-race-day features; the pre-race snapshot is Veikkaus's `stats` block.
- **`startForm` (TASOITUSAJO/RYHMALAHTO) is not `startType` (CAR/VOLT)** — handicap-versus-group is a different axis. The auto-start signal is the per-horse `distanceCode` `a` prefix (`ke`/`ake`/`ly`/`aly`/`akp`), the same convention the km-time suffix uses.
- `shortKilometerTime` (`'18,8'`) is in the same notation as `archive.start.kmTime`, so `parse_km_time()` reads it unchanged; `kilometerTime` (`'1.18.8'`) is the long-form fallback. **It is bare, though: Veikkaus writes `'31,5x'`, `'29,4a'`, `'m18,5a'` and Heppa writes `'31,5'`, `'29,4'`, `'18,5'`.** So `archive.start.kmTime` is *not* uniform after the merge — a Heppa-sourced row has no marker suffix. Compare and analyse on `kmTimeMs` and `autoStart`, never on the string. Verified over the overlap: the strings differ on 30 of 60 rows and the parsed milliseconds agree on 187 of 187.
- Shoe codes are `K`/`E`/`X`, not Veikkaus's `HAS_SHOES`/`NO_SHOES`. Kept verbatim.
- `(date, trackCode)` identifies a meeting — zero duplicates across all 472 events of 2025. `canceled` and `hasPublishedResults` are complements in practice; the crawl tests both anyway.
- **`/horse/{horseId}` is the registry record of the animal**, and `archive.heppa_horse` holds it. Nothing in it is time-varying, so unlike `/horse/{id}/stats` — as-of-now, see below — it cannot leak a result into an as-of-race-day feature. It brings `registerNo`/**`ueln`** (international, so the join to any other registry), an *exact* `birthDate` where `archive.horse` has only a year, `breederName`/`color`/`breedCode`, and `sireId`/`damId` — a pedigree graph with stable ids rather than the name strings `archive.horse` carries. **`/horse/{id}/pedigree` is out of scope** by decision, not by oversight: it adds a second and third generation for another 14,050 requests, and one generation with stable parent ids is enough for the modelling this archive is for. **`/horse/{id}/stats` is now crawled, into `archive.heppa_horse_stat`, and it is reference-only.** It is an as-of-now snapshot, so joining it to a past race leaks that race's result and every result after it — the same rule `heppa_start.horsePriceSum` and `record` carry. It is here for one job that nothing else can do: `starts` per season is the only figure that says how much of a horse's career the archive is missing, because Heppa counts the starts abroad it will not enumerate. One row per (horseId, year, monte), `year = '0'` being the career total; `monte` is in the key because monte and sulky racing keep separate records and both totals arrive as `year` '0'.
- **`birthCountry` is origin; `registrationCountry` is where the horse races.** They differ for any import — `In Love Mearas` is `birthCountry` SE, `registrationCountry` FI — which is why `heppa_start.horseRegistrationCountry` is useless for identity work and reads `FI` for both Elliots. `birthCountry` is the field the same-country name-uniqueness rule actually needs.
- **Heppa writes `'-'` for an absent value**, not an empty field. `blank_to_none()` keeps it out of the tables: a horse with no known breeder is not one bred by `'-'`, and letting it through makes every "how many do we know" count wrong.
- **Crawling `/horse/{id}` does not improve identity resolution**, contrary to what it looks like. 5,232 of the 5,235 horses with no registry id race only on the Swedish simulcast and meta-cards, and Heppa is the *Finnish* registry — it has no record of them, so there is no `/horse/{id}` to fetch. The registry-id path already covers everything it can. What the crawl adds is breeding and origin data, and a cross-registry key.
- **A horse name is unique within an origin country only among contemporaries.** Measured over all 14,050 registry records: 10 name+origin pairs exist, and 9 of them are a name *reused a generation later* — Consta FI 2019/2021, Lemmy FI 2011/2022, Wallander FI 2010/2020. The tenth, `Editor` FI 2020-04-13 and 2020-05-25, is a real same-year same-origin pair. Names also repeat *across* origins on 8 names (Elliot, Furiosa, Gunvald, Kronos, Macchiato, Orzo, Piri-Piri, Spitfire). Birth year is therefore the load-bearing part of the key, not the country: **(name, birth year) collides on 2 pairs in 14,050 — 0.014 %** (`Editor`, and `Elliot` FI/DK six days apart), against 10 for (name, origin) and 1 for all three together. Adding origin would halve it, and is not worth doing: origin only exists for horses that have a registry id, and those never reach the name fallback. `base_horse_key()` is already at its practical limit.
- **Veikkaus birth years are sound.** All 11,851 that can be checked against the registry's exact `birthDate` agree — zero disagreements.
- **Heppa cannot replace the Veikkaus crawl.** It has no odds history and no betting percentages, and its horse-level *statistics* endpoint is as-of-now. Both crawls stay.
- `heppa.hippos.fi/robots.txt` disallows `/heppa/racing`, `/heppa/horse` and `/heppa/person`, and says nothing about `/heppa2_backend`. That is why the Tapestry `RacingHistory` page is off limits even though it has the start list — its form posts under `/heppa/horse`.

**Pipeline:** `__main__.veikkaus()` (argparse) exposes ten subcommands. `backfill --from D [--to D] [--odds] [--limit N] [--retry-failed]` → `crawler.backfill()` crawls Veikkaus into the raw zone; `heppa --from D [--to D] [--limit N] [--retry-failed]` → `heppa.backfill()` crawls the registry's meetings into the same raw zone and the same manifest; `heppa-horses [--limit N] [--retry-failed]` → `heppa.backfill_horses()` crawls one registry record per horse already in the archive; `heppa-foreign [--limit N] [--retry-failed] [--seeds F] [--refetch-from D]` → `heppa.backfill_foreign()` crawls the meetings abroad that `prev_start` names, plus any listed in `foreign_meetings.csv`; `heppa-stats [--limit N] [--retry-failed]` → `heppa.backfill_horse_stats()` crawls the registry's career totals per horse; `leg-percentages [--limit N] [--retry-failed] [--refetch-from D]` → `crawler.backfill_leg_percentages()` crawls the T-pools' per-leg betting percentages for every multi-leg pool the archived `pools` payloads name; `parse` → `parse.parse_all()` loads the raw zone into `archive.*` and runs every recompute; `status` prints manifest counts for both; `crosscheck` → `crosscheck.crosscheck()` validates the two sources against each other; `stats [name]` (aliased `horse`, its name before it counted trainers and drivers too) → `horse_tui.stats_tui()` opens the Textual browser over `archive.heppa_start`.

**Every subcommand refuses a `--db` that is not already there** (`require_db()`, run once before dispatch). DuckDB creates a database for whatever path it is handed, so a mistyped `--db` does not fail — it mints an empty archive and the command then reports zero of everything, which reads as the real archive having gone missing. That happened: `data/veikkaus_data`, the default path minus its suffix, sat in `data/` as a 12 KB empty database. `backfill`, `heppa` and `parse` take `--create-db` for the genuine first run. `status`, `crosscheck` and `stats` only read — `stats` on a read-only connection — and `heppa-horses`, `heppa-foreign`, `heppa-stats` and `leg-percentages` are driven by what is already there — the first three by the parsed archive, `leg-percentages` by the raw zone — so none of the seven has the flag; there is nothing they could do with a database they just made.

**Not part of the pipeline:** `odds_json.py` and `odds_xml.py` are standalone scratch scripts, imported by nothing.

## Automation

None. The repository has no CI workflow — the previous daily job collected the `fi_se` dump, which has been removed. Phase 3 of the strategy (daily entries + results re-fetch, optional odds snapshots near post time) is the intended replacement and is not built.
