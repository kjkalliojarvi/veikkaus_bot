# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Builds a past-performance dataset of Finnish harness racing (ravit) from **two** sources — the Veikkaus open REST API (`https://www.veikkaus.fi/api/toto-info/v1`) for entries and the betting market, and Suomen Hippos's Heppa registry (`https://heppa.hippos.fi/heppa2_backend`) for the official results — crawling both into one raw JSON archive and parsing that into DuckDB. Requires Python >= 3.14, managed with `uv`.

`totodatacollectionstrategy.md` is the spec. Read §2b (the Phase 0 findings) before changing anything that touches the API — it records where the live API contradicts the rest of that plan.

## Commands

```bash
uv sync                                    # install deps into .venv (make install)
uv run veikkaus backfill --from 2021-01-01 # crawl the race calendar into data/raw/ (resumable)
uv run veikkaus heppa --from 2021-01-01    # crawl the Heppa meetings into data/raw/ (resumable)
uv run veikkaus heppa-horses               # crawl one registry record per horse (after heppa + parse)
uv run veikkaus parse                      # raw archive -> archive.* tables
uv run veikkaus status                     # crawl manifest progress, both sources
uv run veikkaus crosscheck                 # do the two sources agree? (strategy §8)
uv run veikkaus stats [name]               # TUI: one horse's or trainer's Heppa starts, seven ways, click a row for the starts (`horse` is an alias; `t` toggles subject)
uv run pytest tests                        # run tests (make run-tests)
uv build                                   # build sdist + wheel (make dist)
```

The CLI entry point is `veikkaus` (defined in `[project.scripts]` → `veikkaus_bot.__main__:veikkaus`).

## Architecture

One pipeline, in two halves that never run together: **fetching and parsing are deliberately separate**, so a parsing bug never costs a re-crawl and the raw responses survive even if the API is retired in the 2027 licensing transition (§4, §10 of the strategy).

- `models.py` — Pydantic models for both APIs: `Card` → `Race` → `Runner` plus `Stat` for Veikkaus, and `HeppaEvent` / `HeppaRaceEntry` → `HeppaRace` / `HeppaStart` for Heppa. Validation only; nothing here fetches.
- `fetcher.py` — `Fetcher` does one request at a time: base delay 2 s ±30 % jitter, retries 429/5xx/timeouts through 30 s → 2 min → 10 min, and raises `CircuitOpen` after 5 consecutive failures. 400/404 mean "nothing there", not an error. `base_url` selects the host, so one instance serves one API and the two sources never spend each other's politeness budget. `store_raw()`/`read_raw()` are the gzipped raw zone, laid out as `data/raw/{meetDate}/card_{cardId}/…`. `VEIKKAUS_CONTACT` sets the contact address in the `User-Agent`.
- `crawler.py` — `Manifest` is the fetch ledger (`archive.manifest`, PK `(endpointType, entityId)`); `enqueue` uses `INSERT OR IGNORE` so re-running a window never re-fetches finished work. `next_pending()` orders by `meetDate DESC, stage ASC` — newest season first (§6), cards before races before per-race payloads — and filters on a tuple of endpoint types, `VEIKKAUS_TYPES` or `HEPPA_TYPES`, so a run of one source never fetches the other's rows. `crawl()` takes the crawl graph as an `expander` callable and knows nothing about either API; `expand()` is the Veikkaus graph. Kill and rerun to resume.
- `heppa.py` — the Heppa crawl graph, same shape as `crawler.py`. Four endpoint types: `heppa_results` (one date range → the meetings), `heppa_races` (one meeting → its races), `heppa_start` (one race → the whole field), and `heppa_horse` (one horse's registry record). Stages 10-13, above the Veikkaus 0-5. Reuses `Manifest`, `Fetcher` and `crawl()` whole. **The horse crawl is a separate opt-in** with its own type tuple, `HEPPA_HORSE_TYPES`, so a one-day results run cannot kick off an eight-hour horse crawl; it is also driven by the *archive* (`SELECT DISTINCT horseId FROM archive.heppa_start`) rather than by a date window, so it has to follow a `heppa` crawl and a `parse`.
- `archive_db.py` — the `archive` schema, its upserts, and the shared DuckDB helpers (`db_ops`, `db_read`, `_insert_many`). Tables: `card`, `race`, `horse`, `start`, `prev_start`, `stat`, `bet_percentage`, `odds_snapshot`, `heppa_event`, `heppa_race`, `heppa_start`, `heppa_horse`, `manifest`.
- `parse.py` — walks the manifest's `done` rows, reads the raw files, upserts. Idempotent. Holds the Finnish km-time parser, `horse_key()`, and the Heppa scalar parsers.
- `crosscheck.py` — read-only validation of the two sources against each other (strategy §8). Builds every report on `archive_db.HEPPA_START_BRIDGE`, the same join the merge uses, so the check cannot drift from what it is checking.
- `horse_stats.py` — the SQL behind `veikkaus stats`: a search and seven breakdowns of `archive.heppa_start` (overall, shoe combination, cart, distance class, start type, `startInterval` bucket, driver), each counting starts, 1st/2nd/3rd and gallops, **for either of two subjects — a horse or a trainer**. **The gallop column overlaps the placings rather than competing with them** — a horse can gallop and still win, and 48,078 of the archive's 51,730 galloping starts were placed at all, 2,832 of them first — so it reads as 'how often did it break under these conditions', never as a fourth outcome. **Distance class strips the `a` prefix** — Heppa's eight `distanceCode` values are four classes and a start-type marker (`ke`/`ake`, `ly`/`aly`, `kp`/`akp`, `pi`/`api`), and the marker is the start-type breakdown's own axis, so keeping it would split every class in two and ask one question twice. Both tables order short-to-long or by starts, never by label: alphabetically the classes come out ke, kp, ly, pi. **The two are the same fact read twice on a Heppa row** — `parse_heppa_auto_start()` derives `autoStart` from that prefix, verified 1:1 over the archive (110,496 `ake` rows, 110,496 auto) — so the start-type table always mirrors the a/bare split; it reads the parsed column rather than re-deriving it because that column is what analysis joins on. Every function takes an open connection, so the SQL is testable the way the rest of the suite tests SQL, and `BREAKDOWNS` is a tuple of `Axis` records in `crosscheck.REPORTS`'s shape — an eighth breakdown is one entry, with no UI code and no drill-down code.

  **Whose starts are counted is a `Subject`, and it is the only thing that varies** — the FROM/WHERE, the drill-down's SELECT list, and the search query. `PLACINGS`, all four label expressions, their sort keys and the absent filter are shared verbatim, which is the whole reason there is no `trainer_stats.py`: a second copy would be a second definition of what `'<= 14 days'` means, exactly the drift `crosscheck` avoids by building on `HEPPA_START_BRIDGE`. The `frm` fragment is a three-part contract — the table is aliased `hs` (every shared expression says `hs.`), it takes exactly one `?` (the identity, so `bucket_starts` builds its parameters without knowing the subject), and it *ends* in a `WHERE` so `Axis.starts` can hang `AND <label> = ?` off it. `Axis.breakdown`/`Axis.starts` are therefore methods taking the subject, not properties.

  **A trainer is identified by `trainerId`, and `_TRAINER_FROM` joins nothing — both halves are load-bearing.** `trainerId` and `trainerName` are non-NULL on all 314,981 rows and every id maps to exactly one name, but 4,665 ids carry only 4,630 distinct names: 35 names belong to two different people, so grouping on the name reports one career for two. And joining `archive.horse` the way the horse subject must would silently drop the **27,430 non-absent rows `RECOMPUTE_HEPPA_START_HORSEKEY` never reached** — 9% of them, starts the trainer really had, and whole trainers whose every start is one of them (365 observed on one id). Nothing needs that table: `hs.horseName` is on the row, and it leads the trainer drill-down's eleven columns. The trainer search is deliberately **one**-stage, unlike the horse's: one id is one trainer, so there is no canonicalisation to resolve; its `horses`/`years` columns exist only as the disambiguator the 35 shared names force, and **the parentheses around its `OR` are load-bearing** — without them the absent filter binds to the id arm alone and a pasted id lists withdrawals.

  **The driver axis is the one capped breakdown, and the cap is named in its title.** The label is `driverFirstName || ' ' || driverLastName`, not either column that looks more like an identity: `driverName` is the short form and unreliable — 113 ids carry a second, *different* person's short name on a handful of rows, so Santtu Raitala's 9,212 starts include one reading `'V Stenman'` — and `driverId` is clean (zero ids carry more than one first+last name) but is 19 digits, and a bucket label is read. The full name is non-NULL and never partial on any of the 293,843 non-absent rows, so no `coalesce`; 3,138 distinct values against 3,143 ids means 5 names belong to two people (557 starts, 0.19%) and merge into one bucket, which the drill-down merges identically. `limit` caps **`breakdown` only** — `starts` stays uncapped, so a bucket on screen still opens exactly its count, and a driver cut by the cap is still reachable. Top 3 covers 79.6% of a horse's starts and 75.2% of a trainer's (median 4 drivers per horse, mean 7.9 per trainer, max 131), so this is the one table that does not sum back to Overall; the title says so, and the sum-back test asserts the exemption rather than tolerating it. `, driver` breaks the ties — 970 trainers have a starts tie straddling the third and fourth driver.

  **`startInterval` bucketing means something subtly different per subject.** The gap is always the *horse's* own, which is a fair trainer question, but the "NULL collapses to one row per horse" argument below **is conditional on the horse subject**: with no join, a trainer's unknown bucket mixes each of its horses' earliest starts with the no-identity rows, and is no longer at most one row. The label string is right for a horse and two tests pin it, so the caveat lives in the `LEGEND` instead. **The label expression that names an axis's buckets is written once**, and both queries are generated from it: `axis.breakdown` groups on it, `axis.starts` filters on it with `= ?` to list the individual starts behind a clicked bucket. Two copies would be two definitions of what `'<= 14 days'` means, free to drift — the reason `crosscheck` builds on `HEPPA_START_BRIDGE` rather than a lookalike. Verified over the 400 busiest horses and all 6,507 of their buckets, and again over the 20 busiest of each subject and all 832 of theirs after the seam went in: a bucket's drill-down returns exactly the count the bucket showed. **Every label is non-NULL by construction, and that is a requirement**: `NULL = ?` is never true, so a NULL label would be a blank row that opens an empty list — hence the `coalesce` around the shoe concatenation, where `||` propagates a NULL, and around `specialCart`. Both are NULL on zero archive rows today, which is data rather than construction. `Overall` has no label at all, so clicking it lists every start. **`absent` rows are excluded in every query**: a withdrawn entry carries shoes and a cart, because entry data is what the registry holds at that point, but never a placement or a `startInterval`, so counting one invents a shoe combination the horse never raced in. The **horse** search is deliberately **two-stage** — a CTE resolves the term to `canonicalKey`s, then the outer query re-joins every `horseKey` of each. Filtering and grouping in one pass restricts the join to the *matched* rows, so a term matching a non-canonical name variant reports a horse that has starts as having none: `humble stance fr` returns 0 starts one-stage and 2 two-stage. The drill-down's `ORDER BY` ends in `programNumber` because a trainer can have two horses in one race, which made the old `(meetDate, raceNumber)` order non-total; it is a no-op for a horse.
- The drill-down's start list is compact on purpose — date, track, race, distance, lane, placing, km time, odds, prize, driver — and its placing column is `coalesce(cast(placement as varchar), disqualifiedCode, '-')`. `heppa_start.placement` is NULL on 36,054 of the 293,843 non-absent rows, so a bare column would render one start in eight as a blank cell, which reads as data we do not have rather than as what happened: a disqualification shows its code (`hpl`, `hll`, `k`, `hlo`) and a start that finished outside the placings shows `-`. Ordered newest first, `raceNumber DESC` within a card, because heats and a final sit on one day. Its last three columns each have a different missing-value story, and the SQL treats them differently: `lane` is `startTrack`, the post, 1-15 and never NULL; `prize` is `prizeWon` in euros and also never NULL, where **0 is what an unplaced start won** — a fact, not a gap, on 128,262 rows; and `odds` is `winOdd` out of hundredths, NULL on the 44,995 local and pony starts with no betting, with `nullif` blanking the 64 rows that store 0, since 1.00 is the floor of a win odd and a zero there means 'not reported'. `printf('%.2f', …)` rather than `round()`, which returns a double and prints a 2.60 price as 2.6, and which would also have to be told what to do with the NULLs.
- `horse_tui.py` — the Textual app (`StatsApp`) and the `stats` CLI handler; widgets only, no SQL. **Which subject is on screen is app state, not a second app**: `t` swaps it and re-runs the term rather than clearing, which is what makes `veikkaus stats 'koivunen'` — no horse by that name — one keypress from the three trainers. The widget tree never changes, because both subjects answer the same seven axes; only the table contents and the hit columns do, and `clear(columns=True)` already handled that. The heading is `name · identity — N starts` for both, because a name is what you searched for while a `trainerId` is 19 digits, and the identity is what every other tool here speaks. `StartsScreen` fills with `add_rows` rather than a row at a time: Overall on the busiest trainer is 3,701 starts over eleven columns. Reads through `db_read` **per query, not per session**, so a browsing session cannot hold the archive against a concurrent `parse` (verified: a read-write open from another process succeeds while the UI is idle). Each breakdown runs inside its own `try`, so a column an older archive lacks costs that one panel instead of the screen. **The click path is a `DataTable` subclass, and every part of that is counter-intuitive.** A single click on a `cursor_type='row'` table posts only `RowHighlighted` — `RowSelected` wants a second click on the same cell — and `DataTable._on_click` calls `event.stop()`, so an app-level `@on(events.Click)` never fires. `ClickableTable.on_click` therefore reads the clicked row from `event.style.meta['row']` (the header is -1, a click below the last row has no `row`, and `self.cursor_row` is still the *old* row there). It posts its **own** message rather than reposting `RowSelected`: `_on_click` posts that itself whenever the clicked cell already holds the cursor, which a freshly filled table's (0, 0) always does, so a `RowSelected` handler opens two panels for one click on the first row — observed, and only on that row. Enter is a subclass binding for the same reason, replacing DataTable's own (bindings merge with the most-derived class winning per key), so mouse and keyboard have exactly one path each. The bucket label rides in the row key, as the hit list's identity does — a `canonicalKey` or a `trainerId`, paired with its display name in `self.labels` because the id is not readable. `StartsScreen` uses `DEFAULT_CSS`, which is auto-scoped, not `CSS`, which is global and would restyle the tables underneath, and it rebinds `q` to close so the reflex does not quit the app.

**`start` vs `prev_start` — the distinction that matters most here.** `archive.start` is one row per (race, horse) built from the runners payload: it describes *the race*, and its `placement`/`kmTime` stop at the paid places because that is all the results endpoint publishes. `archive.prev_start` is built from `runner.prevStarts` — the horse's own career line riding along inside the same payload — and it describes *the careers*: a finishing position for the whole field (observed to 16th), km time, win odd, driver, track, distance and post, per earlier start. It carries `horseKey` rather than the reporting `runnerId`, and is keyed on **(horseKey, meetDate, raceNumber)** — the natural identity of a start.

**Do not key it on `priorStartId`.** That id is assigned per reporting payload, not per start: when a horse races again its whole prevStarts list comes back renumbered as a fresh contiguous block (observed as a constant +1,271,073 offset between two reports of one career). Keying on it stores the same career once per race the horse subsequently ran, and feeds `startInterval` a zero-day gap between each copy. This was shipped and then fixed; the regression tests in `tests/test_archive_db.py` pin it. `raceNumber` belongs in the key because heats and finals put a horse in two races on one card — those are real rows with a genuine zero-day gap.

`prev_start.trackCode` shares a vocabulary with `card.trackAbbreviation`, so the two join on (meetDate, track, raceNumber) — verified against directly-crawled results, which agreed on every overlapping placing.

**`startInterval` is filled in after loading, not per record** (`ArchiveDb.recompute_start_intervals()`, called at the end of `parse_all()`). A reported prevStarts list is a truncated ~8-entry window, so the gap in front of its oldest entry is unknowable from that list alone; and because the window slides forward, whichever report landed last would otherwise decide the stored value. Recomputing over the accumulated table with a window function per `horseKey` makes it deterministic, and re-derives correctly as more dates are crawled in. A horse's earliest start in the archive has no predecessor and keeps the old pipeline's epoch sentinel — **days since 1970-01-01, so it varies with the meet date (~19,600–20,700 observed), not a fixed number.** Filter it in analysis with a threshold well above any plausible gap (`startInterval > 10000`), never by equality. Exactly one row per horse carries it.

**`start.startInterval` and `heppa_start.startInterval` answer a different question, and disagree with `prev_start`'s on purpose** (`ArchiveDb.recompute_cross_source_intervals()`, last in `parse_all()`). `prev_start`'s is a window over `prev_start` alone, partitioned by `horseKey`, with the epoch sentinel on a horse's first row. These two are a window over the **union of all three start-bearing tables**, deduped per horse per `(meetDate, raceNumber)`, partitioned by **`canonicalKey`**, and **NULL** where no predecessor is known — so **never filter them with `startInterval > 10000`; use `IS NULL`.** It must run *after* `recompute_heppa_links()`, which is what writes `canonicalKey` and `heppa_start.horseKey`; run it first and the column comes out almost entirely NULL with no error anywhere.

Three things it does that `prev_start`'s does not. It partitions on `canonicalKey`, because the 182 horses split across 365 keys would otherwise get one inflated career per name variant. It excludes non-runners, by a vote: `archive.start` offers `NOT scratched`, `heppa_start` offers `NOT absent`, `prev_start` **abstains** (it only supplies a date), and a start counts only when every source with an opinion agrees the horse ran. And it counts qualifying starts (`kl`) and retirements (`k`) — the horse went to the gate, which is what a layoff measures; `prev_start.result` filters them downstream.

**The combination-pool meta-cards are excluded from the union, and that was the whole ball game.** `MM`, `Sl`, `T75`, `KUN`, `JAA` and `CIT` (trackNumber 48/88) are not meetings — a meta-card re-lists races that also run under their real track, so counting one puts the horse at two tracks on one day and hands the *next* real start a zero-day gap. Before the filter, 2,514 horse-days were spread over more than one track (2,489 of them a meta-card) and **2,475 of 2,806 zero-day gaps on `archive.start` were spurious**; after it, 356 remain. Dropping them costs almost nothing: of 2,712 meta-card start rows, 8 are the only appearance their horse has that day. **The Swedish simulcasts (trackNumber 57/87, abbreviation ending `-V`) are deliberately kept** — the other card with no Heppa counterpart, but a real race the horse really ran, duplicating nothing, and responsible for 0 multi-track days. Dropping those would inflate the gaps around them.

**`archive.start.scratched = FALSE` and `startInterval IS NULL` can both be true on one row**, and that is the trap most likely to confuse a reader. The runners payload is entry data, so the 175 starts a horse was withdrawn from at the track are not marked there; the vote excludes them from the timeline without laundering `scratched`, which still means "scratched as of entry, per Veikkaus". Every NULL on `archive.start` is one of exactly four things, and they add up: 18,999 scratched, 10,886 a horse's earliest known start, 2,664 a meta-card row, 175 Heppa-`absent` — 32,724 of 288,519, leaving 255,795 filled. On `heppa_start`, **NULL has a fifth meaning: no identity** (29,083 rows `RECOMPUTE_HEPPA_START_HORSEKEY` never reached), so the query that separates the two is `WHERE horseKey IS NOT NULL AND startInterval IS NULL`. **Per horse those five collapse to one**: exclude `absent` and the no-identity rows cannot be joined to a horse at all, so a NULL on a horse's own `heppa_start` rows means exactly "no earlier start known" — at most one row per horse, which is why `horse_stats` gives it its own bucket rather than folding it into the shortest one.

Measured over the 13,666-row overlap with `prev_start`: 12,123 agree, 1,441 replace the epoch sentinel with a real predecessor, 97 are *shorter* because a Heppa-only local meeting or a name-variant of the same horse sits inside the gap, 9 are newly NULL — and exactly **1 is longer**. That one is not a violation: `haahuilee|2021` was entered at Kouvola on 2026-07-29 and withdrawn (Heppa `absent`, `prev_start.result` NULL), so its true layoff into 2026-08-03 is 24 days and not `prev_start`'s 5. The invariant is therefore *a gap may only grow where a non-runner was excluded* — the loose form, "a union can only add predecessors", is wrong, because this union also removes.

**Two residues, both known.** 25 of the 356 remaining zero-day gaps are one malformed card: Veikkaus's Teivo card for 2023-11-07 carries races 9 and 10, which Heppa's Tampere meeting (races 1-8 and 21) does not have and whose horses Heppa places at Pori that day. Everything else with a zero-day gap has its predecessor on the same card, which is the heats-and-finals case and genuine. A *third* residue appearing means something new, exactly as with the two Heppa-less cards above.

**Heppa is where the finishing order actually comes from.** `archive.heppa_start` is one row per (race, horse) from Suomen Hippos's registry, keyed on **(meetDate, trackCode, raceNumber, programNumber)** — Heppa exposes no equivalent of `cardId` or `raceId`. It carries a placing for the whole field, for every Finnish meeting, in every year, without `prev_start`'s condition that the horse raced again. It also carries this race's prize money, a disqualification code per start, and stable registry ids.

The bridge between the two sources is **positional, never name-based**: `(card.meetDate, heppa_track_code(card), race.number, start.startNumber)` against `(meetDate, trackCode, raceNumber, programNumber)`. Matching on horse names instead would break on the country tag Veikkaus appends and Heppa keeps in a separate field. Cards that do not match are the Swedish simulcasts (abbreviation ending `-V`, trackNumber 57/87) and the Veikkaus combination-pool meta-cards (`MM`, `KUN`, `CIT`, `T75`, `Sl`, `JAA`, trackNumber 48/88) — neither is a real meeting and neither has a Heppa counterpart by design.

**`heppa_track_code()`, not bare `upper()`.** Upper-casing gets every real Finnish track right — Veikkaus writes `Ku`, `Tk`, `Jo`, Heppa writes `KU`, `TK`, `JO` — with one exception that cost 28 meetings before it was caught: **Veikkaus spells Härmä both `Hr` and `Hr2`** (Härmä Powerpark and Härmä, both trackNumber 37) and Heppa has only `HR`, so `Hr2` upper-cased to `HR2` and matched nothing. Verified before aliasing: 28 `Hr2` cards, 28 otherwise-unmatched `HR` meetings, the same 28 dates, nothing left over either side, and `Hr` and `Hr2` never share a date. `HEPPA_TRACK_ALIASES` holds it as an explicit alias rather than a rule like "strip trailing digits" — this is one operator's vocabulary quirk, not a pattern. Note the check that missed it originally asked whether two *cards* collide on `(date, upper(abbreviation))`; it never asked whether `Hr2` resolved at all. `crosscheck` now reports unmatched cards grouped by track, where a whole track showing up is the signal.

**The merge into `archive.start` is three statements, and all three are load-bearing** (`recompute_start_from_heppa()`). The obvious single `UPDATE` is not idempotent: it reads `s.placement` to decide `resultSource` and writes `s.placement` in the same statement, so a second run sees Heppa's own fill and relabels it `'veikkaus'`. Instead: reset what Heppa previously contributed (which `resultSource` identifies), merge with `coalesce` so Veikkaus never gets overwritten, then label the remaining placements `'veikkaus'`. That is also why the merge stays away from `winOddsFinal` — one provenance marker cannot honestly describe two columns that can come from different sources on the same row, and the odds history is Veikkaus's anyway. `parse_all()` happens to rebuild `archive.start` from the raw zone first, which would mask the problem; a recompute whose answer depends on how often it has run is a trap regardless.

**Horse identity is resolved through the registry, in both directions** (`recompute_heppa_links()`). `RECOMPUTE_HEPPA_HORSE_ID` fills `archive.horse.heppaHorseId` from the races both sources cover; `RECOMPUTE_HEPPA_START_HORSEKEY` reads that mapping back to stamp `horseKey` onto Heppa rows — including the local and pony meetings, where there is no `archive.start` row to join to. It has to go through `horseId` because **a Heppa start carries no birth year**, so `horse_key()` cannot be computed from one.

**Where the two sources genuinely disagree, and what `start.placement` therefore means.** Over the 73,161 starts both sources place, they agree on 73,145. The exceptions are all explained and none is a bug:

- **16 are post-race disqualifications.** Veikkaus records the order a pool *paid out on*; Heppa records the *official* order after protest. Mikkeli 2021-07-17 race 7 is the shape of it — Veikkaus has Pippi Roc 1st, Heppa has it `hyl` with the whole field promoted a place. Because the merge coalesces and Veikkaus wins, **`archive.start.placement` holds the payout order on those rows**; the corrected order is in `heppa_start.placement`. Which is right depends on whether you are modelling the market or the racing.
- **106 km times differ by exactly a tenth**, Veikkaus always the slower — a rounding convention, concentrated in 2024.
- **175 scratchings differ, and Heppa is right**: the Veikkaus runners payload is entry data, so a horse withdrawn at the track is not marked, while Heppa records it `absent`.
- **~50,000 horse names differ, all but one because of the country tag** — Veikkaus appends `(SE)`, Heppa keeps it in `horseRegistrationCountry`. The one exception is `Black Swan*` vs `Black Swan N`, the same horse under the two naming conventions. This is why the bridge is positional.

**Two real Finnish cards have no Heppa event at all** and never will from this crawl: Vermo 2025-08-16 and Kaustinen 2024-03-24. They are the entire residue of the track-vocabulary investigation — everything else resolved once `Hr2` was aliased — so a third appearing in `crosscheck` means something new, not this.

**`horseKey` joins; `canonicalKey` identifies.** `horse_key()` is name + birth year, and Veikkaus writes an import's name inconsistently — `Humble Stance`, `Humble Stance* (FR)` and `Humble Stance FR* (FR)` are one horse — which split **182 horses across 365 keys**. `RECOMPUTE_HORSE_IDENTITY` groups on `coalesce(heppaHorseId, baseKey, horseKey)` and writes the representative into `archive.horse.canonicalKey`. Every other table still joins on `horseKey`, which is all a Veikkaus payload can produce; **analysis wanting one row per horse must group on `canonicalKey`.**

The ordering inside that coalesce is the whole design. **Names never repeat within an origin country, but they do repeat across countries** — `Elliot` and `Elliot (DK)`, both foaled 2016, are two real horses, and the tag is the only thing separating them. Letting the registry id decide first means the name fallback never gets the chance to merge them; `baseKey` only carries horses the registry never reached (~31 %, mostly pony racing). Note `heppa_start.horseRegistrationCountry` is *not* the field for this — it says where a horse races, and reads `FI` for both Elliots. Origin lives in `/horse/{id}`'s `birthCountry`, which is not crawled.

**`strip_import_markers()` is deliberately conservative.** It drops a parenthesised country tag, and the trailing country letter of the Nordic import convention (`Morell S (SE)`, `Black Swan N (NO)`, `Harley D (DE)`) — but *only when that token agrees with the tag*, being equal to it or its first letter. Trailing tokens are far more often stable suffixes that belong to the name: `Birbone OK (IT)`, `Vulcano OP (IT)`, `Remington XO`, `Aurelia's Pearl KS`, `Tako ÖK* (NO)`. Stripping a trailing letter unconditionally would merge horses that merely share a stem. A token with no tag to agree with is kept, so `Pompom S*` stays distinct from `Pompom* (SE)` here — that pair is one horse, but the registry id says so, not this function.

**DuckDB rules.** Every id and epoch-millisecond value is `BIGINT` (`INTEGER` is 32-bit and `raceId`/`startTime` overflow it). Every table upserts with `INSERT OR REPLACE` — the SQLite `ON CONFLICT` clause inside a `PRIMARY KEY` definition is not supported. `_insert_many()` skips empty batches, which DuckDB's `executemany` rejects, and collapses duplicates *within* a batch against the matching `*_KEY` column positions, so the winning row is chosen in Python rather than by DuckDB's per-statement conflict handling — last row for a key wins, matching the SQL. Keep each `*_KEY` in sync with its table's `PRIMARY KEY` when columns move. Column order in the `*_record()` builders in `parse.py` must stay in sync with the matching `INSERT_*` in `archive_db.py`.

**API facts the schema is shaped around**, all verified in Phase 0 and all easy to get wrong:

- **A runners payload never carries result fields for its own race**, in any era. Placings come from `race.toteResultString` (which names the placed start numbers even when a pool paid fewer than three) with `/race/{raceId}/results` adding km time and the final win odd for the paid places only — so `archive.start.placement` is NULL past third. The full order is recovered from `prev_start` instead, retrospectively.
- **Prev-start `meetDate` is midnight Finnish time expressed in UTC**, so its UTC date is a day early on every row. Parse the meet date from `shortMeetDate` (`dd.mm.yy`) — that is what `parse_meet_date()` does, and it is what lines up with `card.meetDate`. Prev-start `winOdd` is a digit string in hundredths (`'1002'` = 10.02).
- **`prev_start.result` is a raw code**, kept verbatim: numeric placings alongside Finnish outcome codes (`kl` koelähtö, `k` keskeytti, `hpl`/`hll`/`hlo4` hylätty). `parse_result()` fills `placement` only for the numeric ones. Qualifying starts (`kl`, usually raceNumber > 20) are kept rather than filtered — `result` identifies them.
- **A prev-start entry carries no trainer.** It has `driver`/`driverFullName` and nothing else about the connections. `prev_start.coachName` is therefore *sourced from the archive*, not from the payload: `RECOMPUTE_PREV_START_COACH` fills it from the `archive.start` row for that same race, matched on (horseKey, meetDate, raceNumber), which recorded the trainer as of that day. Rows outside the crawl window stay NULL — there is no honest source for them. Never stamp the reporting runner's `coachName` onto these rows: that is the trainer at a *later* race, and with a start re-reported by every subsequent race it would be whichever report happened to land last. The old `main.start` table did exactly that. Track is deliberately not in the join — `prev_start.trackCode` and `card.trackAbbreviation` are not verified to share a vocabulary at every track, and a horse cannot be in two places on one day.
- **`runner.prize` is career earnings, not the race purse** (it equals `stats.total.winMoney`), hence the column name `careerWinnings`.
- **`placing` is a reserved word** in DuckDB's Postgres-derived parser, so the column is `placement`.
- **Km times drop the leading minute** — `'24,9a'` is 1.24,9 from an auto start, 84900 ms. Monté times take a leading `m` (`'m19,6'`); slower times spell the minute out (`'2.05,0'`).
- **`autoStart` comes from `race.startType`, not from the km-time suffix.** Start type is a property of the race, so it is known for every runner — including scratched horses and everyone outside the paid places, none of whom have a km time to read an `a` off. `recompute_auto_starts()` sets it from the race after loading; the suffix survives as a per-horse cross-check (the two agree exactly wherever both exist). Only `CAR_START`/`VOLT_START` have ever been observed and anything else is left NULL. `prev_start` has a `raceStartType` field but the API sends `UNKNOWN` in every entry, so there the suffix is the only per-row signal and the crawled race fills what it can.
- **Historical payloads are thinner than live ones**, and any field can go missing. Only the identifying fields are required — `Card.cardId`/`meetDate`, `Race.raceId`/`cardId`, and `Runner.runnerId`/`raceId`/`horseName`/`startNumber` — because a runner missing one of those cannot be placed at all. **Everything else is Optional on purpose, and tightening one back up trades a whole row for a cosmetic field**: a validation error drops the entire runner, with its start, horse, stats and career line. The API has taken that offer repeatedly (thin pre-2010 cards, absent breeding on a 2005 runner, a 2021 runner with no `coachNameInitials`). Schema drift then shows up as NULLs in the tables rather than as silently dropped rows. `stats` and `prevStarts` ride along only while a card is current, so `archive.stat` and `archive.prev_start` are empty for backfilled years — the career history accumulates from crawling *recent* dates, not old ones.
- **A vacated start number comes back as a `Poissa` ("absent") runner**, not as an omission: always `scratched`, no `coachName` key at all, `gender` usually `UNKNOWN`, and an arbitrary `horseAge` (0–24 across the 19 in the archive). `parse.is_placeholder()` drops them, because each would otherwise become a junk `archive.horse` row — one per distinct age, colliding across tracks and dates — plus an empty start. It tests the horse name and the missing `coachName`, never `driverName`, which arrives as `'Poissa'`, `'- -'`, `'Poissa Poissa'` or `''`.

**Horse identity.** `horse_key()` = `normalize(name)|birthYear`, where normalize folds case and spacing and drops the `*` marker but *keeps* a country tag such as `(SE)` — that tag is what separates an import from a same-named domestic horse. The Veikkaus API exposes no registration number; Hippos's Heppa registry is the authority, and `archive.horse.heppaHorseId` now carries it for the horses the crawl reaches. See `canonicalKey` above for how the two are combined — and note `horse_key()` itself is unchanged on purpose, because it is the only identity a Veikkaus payload can yield on its own.

**Heppa API facts**, all verified live and all easy to get wrong:

- **`startNumber` is the race number and `programNumber` is the horse's start number** — the exact inverse of the Veikkaus vocabulary.
- **Every scalar arrives as a string**, and `'-'` is a common "no value". The models type them `str`; `parse.py` converts. `horseId`/`driverId`/`trainerId` are 19-digit strings kept as `TEXT` — 8.37e18 was observed against a `BIGINT` ceiling of 9.22e18, and the margin is not worth the risk.
- **`placing` has three regimes**: `'0'` is no placing (absent, or disqualified under `hpl`/`hll`/`hrp`/`k`), `'1'`-`'13'` is a real placing, and **`'105'`/`'108'`/`'110'` is 100 + the position a disqualified horse crossed the line in**, always alongside `disqualifiedCode='hlo'`. `parse_placing()` fills `placement` only from the middle regime — the same treatment `parse_result()` gives `prev_start`'s `hlo4`, which encodes exactly the same thing. Filling it would put two horses in one position and break the placings-are-unique check of §8. The raw code survives in `placingRaw`. The column cannot be called `placing`: DuckDB reserves it, as for `archive.start.placement`.
- `disqualifiedCode` uses the same vocabulary as `prev_start.result`. `gallop` is orthogonal — a horse can gallop and still win.
- **`price` is this race's prize money; `horsePriceSum` is career earnings *including* this race.** Veikkaus's `careerWinnings` is the *pre*-race figure in cents. Verified: 142000 cents + 700 € = 2120 €. `horsePriceSum` and `record` therefore leak the result and must never become as-of-race-day features; the pre-race snapshot is Veikkaus's `stats` block.
- **`startForm` (TASOITUSAJO/RYHMALAHTO) is not `startType` (CAR/VOLT)** — handicap-versus-group is a different axis. The auto-start signal is the per-horse `distanceCode` `a` prefix (`ke`/`ake`/`ly`/`aly`/`akp`), the same convention the km-time suffix uses.
- `shortKilometerTime` (`'18,8'`) is in the same notation as `archive.start.kmTime`, so `parse_km_time()` reads it unchanged; `kilometerTime` (`'1.18.8'`) is the long-form fallback. **It is bare, though: Veikkaus writes `'31,5x'`, `'29,4a'`, `'m18,5a'` and Heppa writes `'31,5'`, `'29,4'`, `'18,5'`.** So `archive.start.kmTime` is *not* uniform after the merge — a Heppa-sourced row has no marker suffix. Compare and analyse on `kmTimeMs` and `autoStart`, never on the string. Verified over the overlap: the strings differ on 30 of 60 rows and the parsed milliseconds agree on 187 of 187.
- Shoe codes are `K`/`E`/`X`, not Veikkaus's `HAS_SHOES`/`NO_SHOES`. Kept verbatim.
- `(date, trackCode)` identifies a meeting — zero duplicates across all 472 events of 2025. `canceled` and `hasPublishedResults` are complements in practice; the crawl tests both anyway.
- **`/horse/{horseId}` is the registry record of the animal**, and `archive.heppa_horse` holds it. Nothing in it is time-varying, so unlike `/horse/{id}/stats` — as-of-now, and deliberately not crawled — it cannot leak a result into an as-of-race-day feature. It brings `registerNo`/**`ueln`** (international, so the join to any other registry), an *exact* `birthDate` where `archive.horse` has only a year, `breederName`/`color`/`breedCode`, and `sireId`/`damId` — a pedigree graph with stable ids rather than the name strings `archive.horse` carries. **`/horse/{id}/pedigree` is out of scope** by decision, not by oversight: it adds a second and third generation for another 14,050 requests, and one generation with stable parent ids is enough for the modelling this archive is for. `/horse/{id}/stats` stays out for a different reason — it is as-of-now and would leak results.
- **`birthCountry` is origin; `registrationCountry` is where the horse races.** They differ for any import — `In Love Mearas` is `birthCountry` SE, `registrationCountry` FI — which is why `heppa_start.horseRegistrationCountry` is useless for identity work and reads `FI` for both Elliots. `birthCountry` is the field the same-country name-uniqueness rule actually needs.
- **Heppa writes `'-'` for an absent value**, not an empty field. `blank_to_none()` keeps it out of the tables: a horse with no known breeder is not one bred by `'-'`, and letting it through makes every "how many do we know" count wrong.
- **Crawling `/horse/{id}` does not improve identity resolution**, contrary to what it looks like. 5,232 of the 5,235 horses with no registry id race only on the Swedish simulcast and meta-cards, and Heppa is the *Finnish* registry — it has no record of them, so there is no `/horse/{id}` to fetch. The registry-id path already covers everything it can. What the crawl adds is breeding and origin data, and a cross-registry key.
- **A horse name is unique within an origin country only among contemporaries.** Measured over all 14,050 registry records: 10 name+origin pairs exist, and 9 of them are a name *reused a generation later* — Consta FI 2019/2021, Lemmy FI 2011/2022, Wallander FI 2010/2020. The tenth, `Editor` FI 2020-04-13 and 2020-05-25, is a real same-year same-origin pair. Names also repeat *across* origins on 8 names (Elliot, Furiosa, Gunvald, Kronos, Macchiato, Orzo, Piri-Piri, Spitfire). Birth year is therefore the load-bearing part of the key, not the country: **(name, birth year) collides on 2 pairs in 14,050 — 0.014 %** (`Editor`, and `Elliot` FI/DK six days apart), against 10 for (name, origin) and 1 for all three together. Adding origin would halve it, and is not worth doing: origin only exists for horses that have a registry id, and those never reach the name fallback. `base_horse_key()` is already at its practical limit.
- **Veikkaus birth years are sound.** All 11,851 that can be checked against the registry's exact `birthDate` agree — zero disagreements.
- **Heppa cannot replace the Veikkaus crawl.** It has no odds history and no betting percentages, and its horse-level *statistics* endpoint is as-of-now. Both crawls stay.
- `heppa.hippos.fi/robots.txt` disallows `/heppa/racing`, `/heppa/horse` and `/heppa/person`, and says nothing about `/heppa2_backend`.

**Pipeline:** `__main__.veikkaus()` (argparse) exposes seven subcommands. `backfill --from D [--to D] [--odds] [--limit N] [--retry-failed]` → `crawler.backfill()` crawls Veikkaus into the raw zone; `heppa --from D [--to D] [--limit N] [--retry-failed]` → `heppa.backfill()` crawls the registry's meetings into the same raw zone and the same manifest; `heppa-horses [--limit N] [--retry-failed]` → `heppa.backfill_horses()` crawls one registry record per horse already in the archive; `parse` → `parse.parse_all()` loads the raw zone into `archive.*` and runs every recompute; `status` prints manifest counts for both; `crosscheck` → `crosscheck.crosscheck()` validates the two sources against each other; `stats [name]` (aliased `horse`, its name before it counted trainers too) → `horse_tui.stats_tui()` opens the Textual browser over `archive.heppa_start`.

**Every subcommand refuses a `--db` that is not already there** (`require_db()`, run once before dispatch). DuckDB creates a database for whatever path it is handed, so a mistyped `--db` does not fail — it mints an empty archive and the command then reports zero of everything, which reads as the real archive having gone missing. That happened: `data/veikkaus_data`, the default path minus its suffix, sat in `data/` as a 12 KB empty database. `backfill`, `heppa` and `parse` take `--create-db` for the genuine first run. `status`, `crosscheck` and `stats` only read — `stats` on a read-only connection — and `heppa-horses` is driven by the horses already in the archive, so none of the four has the flag — there is nothing they could do with a database they just made.

**Not part of the pipeline:** `odds_json.py` and `odds_xml.py` are standalone scratch scripts, imported by nothing.

## Automation

None. The repository has no CI workflow — the previous daily job collected the `fi_se` dump, which has been removed. Phase 3 of the strategy (daily entries + results re-fetch, optional odds snapshots near post time) is the intended replacement and is not built.
